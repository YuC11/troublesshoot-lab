# 05 · 接口慢类场景手册（场景 12~16）

> 接口慢的排查心法是**先分层再下钻**：ping 探针（进程级？）→ 接口计时（哪一段？）→
> jstack（线程在等什么？）→ 对应专项（EXPLAIN / 超时配置 / 锁 / 连接池）。
> 场景 16 是综合考核：多因一果的连锁故障。

---

## 场景 12 · 慢 SQL：索引列序错误——「有索引用不上」（含修复闭环 ⭐）

> 企业真实形态：orders 是热点表，索引一应俱全，但其中 user 维度索引
> `idx_created_user(created_at, user_id)` **列序错了**。「我的订单」查询
> `WHERE user_id=? ORDER BY created_at DESC LIMIT 20` 的等值列 user_id 不在
> 索引最左列，违反**最左前缀原则**——索引存在，但优化器没法用它做定位。

**触发**：`POST /api/faults/slow-sql-index-failure/trigger`（确保只剩错误列序索引 + 后台持续慢查询）
**体验**：`curl 'http://localhost:8080/api/order/my-orders?userId=12345'`
**修复**：`POST /api/order/fix-index`（建正确列序索引并删冗余旧索引）→ 复查 →
进阶 `POST /api/order/fix-index?covering=true`（覆盖索引）→ `POST /api/order/reset-index` 复位

### 【模拟告警】
> 【P1告警】/api/order/my-orders P99 2.8s（阈值 500ms），慢查询日志新增 214 条/5min
> 命中 orders 表；DBA 反馈 orders 表索引齐全——索引存在但优化器不选它

### 【第0现场 · 可观测性视角】
- 指标：单接口 P99 高 + **DB 侧慢查询计数同步上涨**（应用与 DB 告警同屏出现是关键）；
- 链路：Trace 瀑布图 Span 停在 `JDBC SELECT orders`，该 Span 占请求总耗时 95%+；
- 拓扑：应用 → MySQL 这条边的 RT 变红。**慢在数据库**已被观测系统直接指认——
  但「为什么慢」要登机用 EXPLAIN 回答。

### 【定位路线图】
```
接口计时确认慢 → EXPLAIN 看执行计划 → 看三个判决字段: type / key / rows
→ type=index(全索引扫描)或 ALL + key 用不上正确索引 = 「索引失效/列序错误」
→ 对照 SHOW INDEX 找出「存在的索引 vs 查询需要的索引前缀」 → 建正确列序索引
→ 删冗余旧索引(建新必删旧) → 复查耗时与执行计划(type=ref) → 覆盖索引进阶
```

### 【分步排查】
**Step 1 · 亲测慢**
```bash
curl 'http://localhost:8080/api/order/my-orders?userId=12345'
```
<details><summary>实测输出（100 万行 × 29 列企业级宽表）</summary>

```json
{"userId":12345,"matched":1,"costMs":7268, ...}
```
注意：这里 7.2s = **纯扫描耗时 + 连接池排队**（池只有 2 个连接，后台慢查询正占着，
你的请求在 HikariPool 排队——这正是场景 16 的预演）。纯查询耗时见 Step 2 的
mysql CLI 直连：约 240ms（本机 NVMe、百万行索引全扫）。**生产 5 千万行 + 网络往返
≈ 数秒到数十秒**——这就是为什么「测试环境好好的」：索引问题是随数据量长出来的。
</details>

**Step 2 · 拿纯查询耗时（绕开应用，直连 DB 排除排队干扰）**
```bash
mysql -h127.0.0.1 -uroot -prootroot troubleboot_lab -e \
  "SELECT order_id FROM orders WHERE user_id=12345 ORDER BY created_at DESC LIMIT 20;"
```
<details><summary>实测（macOS time）</summary>

```
real  0m0.241s    ← 纯扫描 241ms（应用侧 7.2s 的大头其实是池排队）
```
</details>

**Step 3 · 执行计划——三个判决字段**
```bash
curl 'http://localhost:8080/api/order/explain?userId=12345'
```
<details><summary>实测输出（故障态 vs 修复态）</summary>

```json
// ❌ 故障态：表上有 idx_created_user, 但优化器只能拿它做「全索引扫描」
{ "type": "index",                    // ← 不是 ref! 全索引扫描(比 ALL 略好, 本质同类)
  "possible_keys": null,              // ← 没有任何索引能用于「定位」
  "key": "idx_created_user",          // ← 却选了它当扫描顺序(满足 ORDER BY DESC)
  "rows": 20, "Extra": "Using where; Backward index scan" }
// 残忍之处: 优化器「用了索引」却把索引当全表扫的替身——因为最左列是 created_at,
// 而 WHERE 等值列 user_id 在第二位, 无法做树定位(最左前缀原则)

// ✅ 修复态（建 idx_user_created(user_id, created_at) 后）
{ "type": "ref",                      // ← 索引定位查找
  "possible_keys": "idx_user_created",
  "key": "idx_user_created", "ref": "const",
  "rows": 1, "Extra": "Backward index scan" }
```
type 评级速记：`system > const > eq_ref > ref > range > index > ALL`。
**`index`（全索引扫描）是最有迷惑性的一档**——看到它别以为索引工作正常，
它意味着「把整棵索引树扫了一遍」。线上 OLTP 常态应该是 `ref/eq_ref/const`。
</details>

**Step 4 · 看看表上到底有哪些索引（病灶的反差感）**
```bash
mysql ... -e "SHOW INDEX FROM orders"
```
<details><summary>实测索引清单</summary>

```
PRIMARY, uk_order_no, idx_created_user(created_at,user_id)   ← 病灶: 列序反了
idx_merchant_status_created, idx_status_created, idx_pay_time
```
六个索引的热点表照样慢——**索引数量 ≠ 索引有效**。
</details>

**Step 5 · 修复并验证闭环**
```bash
curl -X POST http://localhost:8080/api/order/fix-index
# → 已建 idx_user_created(user_id, created_at) 并删除冗余旧索引 idx_created_user
mysql ... -e "SELECT order_id FROM orders WHERE user_id=12345 ORDER BY created_at DESC LIMIT 20;"
# → real 0m0.018s   实测 241ms → 18ms(含CLI连接开销, 纯查询<1ms), 快 13 倍+
```

**Step 6 · 进阶：覆盖索引（免回表）**
```bash
curl -X POST 'http://localhost:8080/api/order/fix-index?covering=true'
# → 已建 idx_user_covering(user_id, created_at, order_status, pay_amount)
#   并删除冗余的 idx_user_created(覆盖索引已含其前缀)
curl 'http://localhost:8080/api/order/explain?userId=12345'
# → Extra: "Backward index scan; Using index"   ← Using index = 整个查询在索引上完成, 不回表
```

**Step 7 · 延伸教具：四大索引杀手对照（同表同数据，坏/好写法同屏）**
```bash
curl 'http://localhost:8080/api/order/index-killer?killer=cast'   # 隐式类型转换
curl 'http://localhost:8080/api/order/index-killer?killer=like'   # 前导通配 LIKE
curl 'http://localhost:8080/api/order/index-killer?killer=func'   # 列上套函数
```
<details><summary>实测数据（100 万行宽表）</summary>

```
[cast] 坏 247ms vs 好 1ms   WHERE order_no = 202500000001   (列是VARCHAR却比数字→每行隐式转换, uk_order_no 失效)
[like] 坏 358ms vs 好 1ms   WHERE buyer_remark LIKE '%生日%' (前导通配无法走索引; '生日%' 才能走)
[func] 坏 111ms vs 好 2ms   WHERE DATE(created_at)='2025-06-01' (索引列参与函数即失效; 改范围查询)
```
第四个杀手就是本场景的主角——**复合索引列序不符最左前缀**。
</details>

### 【根因】
复合索引 `idx_created_user(created_at, user_id)` 列序错误：最左前缀原则要求
**等值条件列放最前，范围/排序列放后面**。本查询等值列 user_id 被排到了第二位，
索引退化为「可扫描、不可定位」。典型成因：先按时间查询建了索引，后来加了
按用户查询的代码，「表上有 user 相关索引」的错觉让所有人放过了一验收。

### 【修复对比】
```sql
-- ❌ 病灶: 等值列不在最左 → 只能全索引扫描
CREATE INDEX idx_created_user ON orders(created_at, user_id);

-- ✅ 修复: 等值列在前、范围/排序列在后 → ref 定位
CREATE INDEX idx_user_created ON orders(user_id, created_at);
-- 进阶: 覆盖索引(把 SELECT 的列也装进索引, 免回表)
CREATE INDEX idx_user_covering ON orders(user_id, created_at, order_status, pay_amount);

-- ⚠️ 建新必删旧: 留着旧索引只会拖累写入(每个索引都是一次有序写)
DROP INDEX idx_created_user ON orders;
```

### 【预防】
- 索引评审三问：这条 SQL 的等值列是不是索引最左前缀？区分度够不够？会不会与现有索引冗余？
- 上线前用**生产量级**数据 EXPLAIN（低数据量环境的执行计划没有代表性）；
- 慢查询日志 `long_query_time=0.5s` 常态化；`type=index/ALL` 与 `key 与预期不符` 都要报警；
- 建新索引的同时下线被替代的旧索引（索引治理：只增不减 = 写入放大慢性病）。

### ⭐ Arthas
```
trace com.lab.troubleshoot.web.OrderController myOrders '#cost > 100'
# 树状耗时: JDBC 段占比一目了然, 只看慢调用
watch com.lab.troubleshoot.repository.LabRepository findMyOrders '{params,throwExp}' -x 1 -n 2
```

## 场景 13 · N+1 查询：慢查询日志抓不到的慢

**触发**：`POST /api/faults/slow-n-plus-1/trigger`（打开逐条 SQL 日志）
**体验**：`curl 'http://localhost:8080/api/order/top-spenders?limit=500&mode=n%2B1'`（病灶）
对照：`curl '...&mode=batch'`（修复版）

### 【模拟告警】
> 【P2告警】/api/order/top-spenders P99 1.9s；慢查询日志（1s 阈值）**无新增**，
> DB CPU 正常 —— 接口慢但数据库「无辜」

### 【第0现场 · 可观测性视角】
- 指标：接口慢，但 DB 慢查询计数、DB CPU 均正常（**这是 N+1 的指纹**）；
- 链路：Span 总耗时高，但其中每条 SQL Span 都只有 1~2ms —— 需要看 Span **数量**；
- 需要 SQL 执行计数（p6spy / Druid 监控 / OTel DB instrumentation 统计）才能看清：
  一次请求 501 条 SQL。

### 【定位路线图】
```
接口计时(慢) → DB 无慢查询(矛盾点!) → 数 SQL 条数(SQL日志/连接监控) →
一次请求 N+1 条 → 找到循环查询的代码 → 改批量
```

### 【分步排查】
**Step 1 · 对照体验**
<details><summary>实测输出（order_item 300 万行）</summary>

```json
// 病灶版 mode=n+1
{"mode":"n+1","users":500,"orderItemsFetched":3091,"sqlCount":501,"costMs":86}
//                                                 ↑ 501 条 SQL   ↑ 86ms

// 修复版 mode=batch
{"mode":"batch","users":500,"orderItemsFetched":3091,"sqlCount":2,"costMs":13}
//                                                 ↑ 2 条 SQL    ↑ 13ms
```
本机 loopback 网络往返≈0.2ms/条，501 条才 86ms；**生产跨机房 1~3ms/条时，
同样代码就是 1~2s**——N+1 的伤害与网络延迟成正比。
</details>

**Step 2 · 让 SQL 刷屏可见**：触发场景后（verbose 已开），应用日志实时输出
`[SQL #317] 1 ms | SELECT * FROM order_item WHERE user_id=...` ——
肉眼确认「接口没死循环，是 SQL 在一条条跑」。

### 【根因】
先查 500 个用户，再**循环**逐个查 order_item 明细：1 + N 条 SQL。ORM（JPA 的
懒加载、MyBatis 嵌套 select）是 N+1 的高发区——框架替你写的循环最容易忽视。

### 【修复对比】
```java
// ❌ N+1
List<User> users = userDao.findUsers(limit);
for (User u : users) {
    u.setItems(itemDao.findByUser(u.getId()));      // 循环内逐条查询
}

// ✅ 两条 SQL 批量拿全, 内存归并
List<User> users = userDao.findUsers(limit);
Map<Long, List<OrderItem>> byUser = itemDao.findByUserIds(ids)   // WHERE user_id IN (...)
        .stream().collect(groupingBy(OrderItem::getUserId));
users.forEach(u -> u.setItems(byUser.getOrDefault(u.getId(), List.of())));
// JPA 对应: @EntityGraph / JOIN FETCH; MyBatis: 嵌套 resultMap(一次JOIN) 优于嵌套 select
```

### 【预防】
- SQL 执行次数监控（Druid/p6spy 统计「每请求 SQL 数」，突增即报警）；
- Code review 盯紧「循环体内出现 DAO 调用」；
- ORM 懒加载禁止出现在循环与序列化路径。

### ⭐ Arthas
```
trace com.lab.troubleshoot.repository.LabRepository findItemsByUserIndexed '#cost>1' -n 20
# 每次调用虽快, 但 trace 的调用次数计数(N 次调用)直接暴露 N+1
watch com.lab.troubleshoot.web.OrderController topSpenders '{params,#this}' -x 1 -n 1
```

## 场景 14 · 慢外部依赖：无超时拖垮全站

**触发**：`POST /api/faults/slow-external-no-timeout/trigger`（25 个无超时 caller 打内置慢下游）
**对照体验**：
```bash
curl -w '%{http_code} %{time_total}s\n' -o /dev/null http://localhost:8080/api/payment/no-timeout   # hang 3s+
curl -w '%{http_code} %{time_total}s\n' -o /dev/null http://localhost:8080/api/payment/with-timeout # 503 快速失败
```

### 【模拟告警】
> 【P0告警】全站接口 P99 3.4s，Tomcat 线程池打满（busy 50/50）；
> 下游 payment-svc P99 从 45ms 恶化至 3s —— 疑似级联故障

### 【第0现场 · 可观测性视角】
- 拓扑：**下游服务先变红**，上游随后（因果顺序在拓扑/时间线上非常清晰）；
- 链路：本服务 Span 不慢，慢的是下游 Span —— 但上游线程被占满的连锁反应
  表现为「本服务全接口劣化」；
- 线程指标：Tomcat busy 线程数贴顶 + 大量请求排队 —— 级联故障的标准三联。

### 【定位路线图】
```
ping 仍快(进程没死) → jstack 看 Tomcat 线程在等什么 → 一排 socketRead0 +
调用栈指向同一下游 → 观测拓扑确认该下游 RT 恶化 → 检查 HTTP 客户端配置(无超时!)
```

### 【分步排查】
**Step 1 · 分层**：`curl http://localhost:8080/api/health/ping` → 2ms（实测 0.002s）
进程健康 → 不是 GC/死锁 → 是「线程被占满」或特定链路。

**Step 2 · 看线程在等什么**：`jstack <pid> | grep -A 8 'http-nio-8080-exec' | head -20`
<details><summary>实测特征</summary>

```
"http-nio-8080-exec-5" ... RUNNABLE
	at java.base@21.0.11/java.net.SocketInputStream.socketRead0(Native Method)   ← 挂在读 socket
	...java.net.Socket$SocketInputStream.read
	...org.springframework.http.client...SimpleBufferingClientHttpRequestexecute
	...PaymentDemoController.payNoTimeout(...)    ← 业务帧指向支付调用
```
多个 exec 线程**同样的栈** + 观测系统里下游 RT 恶化 = 无超时等待下游的铁证。
</details>

**Step 3 · 对照实验**（本场景内置）：with-timeout 版同条件下 0.5s 快速失败（实测 503/0.53s），
no-timeout 版 3.0s+ —— 一行配置的差距用数据说话。

### 【根因】
`RestTemplate` 默认**不设超时**（connect/read 无限等待）。下游从 50ms 恶化到 3s，
每个请求挂 3 个 Tomcat 线程干等，线程池打满殃及全站。

### 【修复对比】
```java
// ❌ 默认构造 = 无超时
RestTemplate rt = new RestTemplate();

// ✅ 超时三件套 + 熔断兜底
SimpleClientHttpRequestFactory f = new SimpleClientHttpRequestFactory();
f.setConnectTimeout(500);   // 建连 500ms
f.setReadTimeout(500);      // 读响应 500ms —— 必须显式设置!
RestTemplate rt = new RestTemplate(f);
// 生产再叠加 Resilience4j 熔断: 下游错误率>50% 时直接快速失败, 半开探测恢复
```

### 【预防】
- HTTP 客户端超时是**上线 checklist 必选项**（连接/读/总超时分别评审）；
- 熔断器常态化（Sentinel/Resilience4j），核心链路对弱依赖做降级；
- 全站接口挂但 ping 快 → 第一反应查下游与线程池，而不是自己的业务代码。

### ⭐ Arthas
```
thread --state RUNNABLE | grep -A 5 socketRead    # 成排 socketRead 等待
trace com.lab.troubleshoot.web.PaymentDemoController '*' '#cost>1000'   # 慢在外部调用段
```

## 场景 15 · 锁竞争：锁内做慢 IO

**触发**：`POST /api/faults/slow-lock-contention/trigger`（40 个争抢线程）
**体验**：`curl http://localhost:8080/api/inventory/deduct`（排队恶化）

### 【模拟告警】
> 【P1告警】/api/inventory/deduct P99 8.2s（正常 2.1s），随并发升高**线性**恶化；
> 线程 dump 40+ 线程 BLOCKED 等待同一 monitor

### 【第0现场 · 可观测性视角】
- 指标：单接口 RT 随并发**线性**恶化（无外部依赖变化、无 GC 异常）——
  「RT/并发」斜率突变是锁竞争的指纹；
- 链路：Span 慢在自身（无下游慢 Span、无 DB 慢 Span）；
- 线程指标：BLOCKED 状态线程数与并发数同步（若有线程状态监控）。

### 【定位路线图】
```
jstack 统计 BLOCKED 数量 → 全部 waiting to lock 同一个地址 <0x...> →
看持锁线程(owner)在锁内做什么(sleep/socketRead = 锁内慢IO) → 缩小锁范围
```

### 【分步排查】
**Step 1 · 数阻塞**：`jstack <pid> | grep -c 'BLOCKED'` →（实测 39）
**Step 2 · 看阻塞现场**：
<details><summary>实测输出</summary>

```
"lock-contender" #277 ... BLOCKED (on object monitor)
	at com.lab.troubleshoot.service.InventoryService.deductWithWideLock(InventoryService.java:34)
	- waiting to lock <0x000000016ec7f578> (a com.lab.troubleshoot.service InventoryService)
	                                                                                     ↑ 全员等同一把锁
```
再找 owner：搜 `locked <0x000000016ec7f578>`，它的栈是 `Thread.sleep` ——
**持锁者在锁内睡觉**，其他 39 个排队。判决完成。
</details>

### 【根因】
`synchronized` 方法内做 2s 慢操作（模拟锁内 RPC）：吞吐被锁串行化，
理论 500/s 的接口变成 1/2s = 0.5/s。

### 【修复对比】
```java
// ❌ 整个方法上锁, 锁内含 2s 远程调用
public synchronized void deduct(long holdMs) throws InterruptedException {
    rpcCall();            // 2s, 在锁内!
    stock--;              // 真正需要保护的就这一行
}

// ✅ 缩小锁范围: 只锁共享数据修改; 远程调用移出锁外
String plan = rpcCall();                       // ① 锁外做慢 IO(或预取/异步化)
synchronized (this) { applyPlan(plan); }       // ② 锁内只做纯内存计算
// 进一步: CAS/LongAdder/分段锁/库存预扣+异步落库, 按吞吐要求逐级升级
```

### 【预防】
- review 红线：**锁内禁止 IO/RPC/sleep**（锁内代码按纳秒级标准审查）；

## 场景 16 · 连接池耗尽：慢 SQL 的连锁反应（综合考核 ⭐）

**触发**：`POST /api/faults/slow-db-pool-exhausted/trigger`（6 个连接占坑线程 vs 池上限 2）
**受害体验**：`curl http://localhost:8080/api/order/1`（正常 1~3ms → 秒级排队）

### 【模拟告警】
> 【P0告警】所有 DB 接口批量报错 Connection is not available, request timed out after
> 10000ms；同时段慢查询日志新增 orders 全表扫描记录 —— 疑似连接池耗尽

### 【第0现场 · 可观测性视角】
- 指标：HikariCP 池指标（active 贴顶 = maximumPoolSize、pending 线程数 > 0、
  `connection_acquire_time` 飙升）+ **同期慢 SQL 告警**（因果双证据）；
- 链路：所有 DB 接口 Span 停在「获取连接」阶段（还没走到 SQL）；
- 全站 DB 接口同时挂 + ping 正常 —— 池级/依赖级故障特征。

### 【定位路线图】（综合运用 12/14 的方法）
```
ping 快 → jstack: 受害线程停在 HikariPool.getConnection(不是 SQL!) →
连接池指标 active=2/2 满载 → 谁占着连接? → 慢查询日志/DB processlist
→ 全表扫描慢 SQL 长期持有连接 → 连锁: 慢SQL → 连接占满 → 全站DB接口挂
```

### 【分步排查】
**Step 1 · 受害接口计时**：`time curl -m 15 http://localhost:8080/api/order/1`
<details><summary>实测输出</summary>

```
$ curl http://localhost:8080/api/order/1
{"order_id":1,...,"costMs":1013}    ← 平时 1~3ms, 现在 1s+(8并发实测≈8s 排队)
real  0m1.028s
```
8 个并发实测全部 ~8s（排队等连接）；并发更大时会触发
`SQLTransientConnectionException ... timed out after 10000ms`（connection-timeout）。
</details>

**Step 2 · 受害线程栈（决定性证据）**
<details><summary>实测 jstack</summary>

```
"http-nio-8080-exec-3" ... WAITING
	at ...SynchronousQueue.poll(SynchronousQueue.java:338)
	at com.zaxxer.hikari.util.ConcurrentBag.borrow(ConcurrentBag.java:151)
	at com.zaxxer.hikari.pool.HikariPool.getConnection(HikariPool.java:162)   ← 停在等连接!
	at ...JdbcTemplate.query(...)
	... OrderController.byId(...)
```
业务线程没在跑 SQL、也没在等下游 —— 它在**等连接**。这是与场景 12/14 的分水岭。
</details>

**Step 3 · 找占坑者**：DB 侧 `SHOW PROCESSLIST`（占坑的 SLEEP/慢查询一目了然）；
应用侧看慢查询日志（场景 12 的告警同期出现）。

### 【根因链】（多因一果，综合考核的意义）
```
慢 SQL 全表扫描(场景12的病) → 每条查询占连接 3s+ →
池只有 2 个连接(配置病) → 正常毫秒级查询也拿不到连接 → 全站 DB 接口挂
```
单独看每一环都不致命，组合起来就是 P0。

### 【修复】（分层次，先止血再治本）
```yaml
# ① 应急: 扩池(治标, 慢 SQL 还在)
hikari:
  maximum-pool-size: 20        # 经验起点: CPU核数*2 + 磁盘数, 压测校准
```
```sql
-- ② 治本: 干掉慢 SQL(回到场景 12 的索引修复)
CREATE INDEX idx_orders_user_id ON orders(user_id);
```
```java
// ③ 防扩散: 大查询走只读从库/独立小池, 不与在线交易抢连接
```

### 【预防】
- Hikari 指标（active/pending/await）必上监控；池大小写进容量文档；
- 慢 SQL 告警与连接池告警做**关联分析**（本场景的因果就是最常见关联）；
- 大促/新功能上线前评估「最长查询耗时 × 并发 > 池大小」的排队风险。

## 附 · 企业级订单域建模与索引设计（本演练的 schema 解读）

### A. orders 为什么长这样（29 字段宽表的设计逻辑）

| 字段组 | 字段 | 设计理由 |
|---|---|---|
| 双标识 | `order_id`(PK,雪花) + `order_no`(UNIQUE) | 内部主键自增友好；对外单号可读且防重（客服/支付回调认它） |
| 主体与渠道 | `user_id` / `merchant_id` / `channel` | 买卖家双边 + 流量归因 |
| 状态机 | `order_status` TINYINT + `pay_time/delivery_time/finish_time/cancel_time` | 状态用小整数+枚举（VARCHAR 存状态是大忌）；每个状态独立时间戳支撑审计与超时扫描 |
| 四金额 | `total/discount/pay/freight_amount` DECIMAL(12,2) | 金额拆分才能对账平账；DECIMAL 定点（FLOAT 是事故） |
| 收货快照 | `receiver_*` / `address` | **下单时刻固化**——用户后来改地址不影响历史订单（新手最常漏） |
| 软删与并发 | `is_deleted` + `version`(乐观锁) | 审计要求物理不删；并发改单用版本号 |
| 子表 | `order_item`(300万,SKU 快照) / `order_payment`(多次尝试) / `order_status_log`(流转审计) | 主子表是订单域标配；快照字段让历史不可变 |

### B. 索引清单——每个索引都挂在一条真实查询上

| 索引 | 服务的查询 | 原则 |
|---|---|---|
| PK(order_id) | 点查 | |
| uk_order_no | 客服查单/支付回调 | UNIQUE 顺带防重 |
| **idx_user_created(user_id, created_at)** | 「我的订单」（C 端最热） | **等值列最左、范围/排序列靠后**——本手册场景 12 的正反两面 |
| idx_merchant_status_created | 商家后台按状态筛单 | 等值(merchant,status) 在前，时间在后 |
| idx_status_created | 定时任务扫「待支付超时」 | 低区分度列必须配合高区分度/范围列 |
| idx_pay_time | 对账任务按支付时段 | |
| 覆盖索引变体 | 列表页免回表 | SELECT 的列全部入索引 → `Using index` |

**反面清单**：低区分度单列索引（status/sex 单独建）；已有 (a,b) 再建 (a)（冗余）；
`LIKE '%x'`、`DATE(col)=`、列参与运算、隐式类型转换——**四大索引杀手**（教具：
`GET /api/order/index-killer?killer=cast|like|func`，加上本场景的列序错误共四个半）。
**建新必删旧**：索引只增不减 = 每行写入多付一份有序写成本（慢性写入放大）。

### C. 当单表过大之后（亿级订单的真实归宿）

1. **分库分表**：按 `user_id` hash 分 16/64 张表——「我的订单」天然路由；
   代价是商家维度查询失去全局索引 → 异构索引表或走 ES。
2. **冷热分离**：近 3 个月热数据留在主库，历史归档至廉价存储（按 `created_at`）。
3. **多维度查询外移**：商家后台/运营多维检索走 ES 宽表或 ClickHouse，
   MySQL 只扛交易主链路（点查 + 状态机推进）。
4. **容量红线**：单表经验值 2000 万~5000 万行或 20GB 就要启动拆分评审——
   不要等慢查询报警才动手（本演练 100 万行只是教学缩样）。

> 分表后的连锁问题（分布式事务/跨分片查询/全局唯一 ID）超出本演练范围，
> 但「为什么-orders-要冗余 user_id 在 order_item」这类字段设计，答案都在这里。
