# 05 · 接口慢类场景手册（场景 12~16）

> 接口慢的排查心法是**先分层再下钻**：ping 探针（进程级？）→ 接口计时（哪一段？）→
> jstack（线程在等什么？）→ 对应专项（EXPLAIN / 超时配置 / 锁 / 连接池）。
> 场景 16 是综合考核：多因一果的连锁故障。

---

## 场景 12 · 慢 SQL：缺索引全表扫描（含修复闭环 ⭐）

**触发**：`POST /api/faults/slow-sql-no-index/trigger`（确保无索引 + 后台持续慢查询）
**体验**：`curl 'http://localhost:8080/api/order/query-by-user?userId=12345'`
**修复**：`POST /api/order/fix-index` → 再查同接口 → `POST /api/order/reset-index` 复位

### 【模拟告警】
> 【P1告警】/api/order/query-by-user P99 2.8s（阈值 500ms），慢查询日志新增 214 条/5min，
> 均命中 orders 表全表扫描；MySQL 服务器 read CPU 升高

### 【第0现场 · 可观测性视角】
- 指标：单接口 P99 高 + **DB 侧慢查询计数同步上涨**（应用与 DB 告警同屏出现是关键）；
- 链路：Trace 瀑布图 Span 停在 `JDBC SELECT orders`，该 Span 占请求总耗时 95%+；
- 拓扑：应用 → MySQL 这条边的 RT 变红。**慢在数据库**已被观测系统直接指认。

### 【定位路线图】
```
接口计时确认慢 → EXPLAIN 看执行计划 → type=ALL + rows≈全表 = 缺索引判决
→ 建索引 → 复查耗时与执行计划(type=ref) → 复盘为什么上线时没暴露(数据量)
```

### 【分步排查】
**Step 1 · 亲测慢**
```bash
curl 'http://localhost:8080/api/order/query-by-user?userId=12345'
```
<details><summary>实测输出（100 万行、Apple Silicon 本地库）</summary>

```json
{"userId":12345,"matched":0,"costMs":252}
```
本机 NVMe 全表扫描 100 万行 ≈ 250ms；**生产 5 千万行 + 网络往返 ≈ 数秒到数十秒**。
（这就是为什么「测试环境好好的」——索引问题是随数据量长出来的。）
</details>

**Step 2 · 执行计划**
```bash
curl 'http://localhost:8080/api/order/explain?userId=12345'
```
<details><summary>实测输出（故障态 vs 修复态）</summary>

```json
// ❌ 故障态：全表扫描
{ "table": "orders", "type": "ALL", "key": null, "rows": 992173 }
//          ↑ALL=全表       ↑没用任何索引   ↑预估扫描 99 万行

// ✅ 修复态（建索引后）
{ "table": "orders", "type": "ref", "key": "idx_orders_user_id", "rows": 4 }
//                         ↑ref=索引查找   ↑用了索引              ↑只扫 4 行
```
type 评级速记：`system > const > eq_ref > ref > range > index > ALL`，
线上 OLTP 出现 `ALL` 基本等于判了死刑。
</details>

**Step 3 · 修复并验证闭环**
```bash
curl -X POST http://localhost:8080/api/order/fix-index    # 建索引(1M 行约 0.7s)
curl 'http://localhost:8080/api/order/query-by-user?userId=12345'
# → {"costMs":2, ...}   实测 252ms → 2ms，125 倍
```

### 【根因】
`orders.user_id` 无索引 + `remark LIKE '%ab%'` 双重叠加；前者是主因（后者无法走索引）。

### 【修复对比】
```sql
-- ✅ 修复: 对高频等值查询列建索引
CREATE INDEX idx_orders_user_id ON orders(user_id);
-- 复合场景建覆盖索引可再消回表: (user_id, created_at, amount)
```
```java
// 顺带的代码层修复: LIKE '%x%' 前导通配无法走索引, 改右匹配或全文索引
WHERE remark LIKE 'ab%'     -- 可走索引(最左前缀)
```

### 【预防】
- 慢查询日志 `long_query_time=0.5s` 常态化 + DBA 巡检；
- 上线前用**生产量级**数据 EXPLAIN 评审（低数据量环境的执行计划没有代表性）；
- `LIKE '%x'`、函数包列、隐式类型转换是索引三大杀手，review 清单化。

### ⭐ Arthas
```
trace com.lab.troubleshoot.web.OrderController queryByUser '#cost > 100'
# 输出树状耗时: `#cost>100` 只看慢调用, JDBC 段耗时占比一目了然
watch com.lab.troubleshoot.repository.LabRepository findByUserSlow '{params,@java.lang.System@currentTimeMillis()}' -x 1 -n 2
```

## 场景 13 · N+1 查询：慢查询日志抓不到的慢

**触发**：`POST /api/faults/slow-n-plus-1/trigger`（打开逐条 SQL 日志）
**体验**：`curl 'http://localhost:8080/api/order/top-spenders?limit=500&mode=n%2B1'`（病灶）
对照：`curl '...&mode=batch'`（修复版）

### 【模拟告警】
> 【P2告警】/api/order/top-spenders P99 1.9s；慢查询日志（1s 阈值）**无新增**，
> DB CPU 正常 —— 接口慢但数据库「无辜」

### 【第0现场 · 可观测性视角】
- 指标：接口慢，但 DB 慢查询计数、DB CPU 均正常（**这是 N+1 的指纹**）；
- 链路：Span 总耗时高，但其中每条 SQL Span 都只有 1~2ms —— 需要看 Span **数量**；
- 需要 SQL 执行计数（p6spy / Druid 监控 / OTel DB instrumentation 统计）才能看清：
  一次请求 501 条 SQL。

### 【定位路线图】
```
接口计时(慢) → DB 无慢查询(矛盾点!) → 数 SQL 条数(SQL日志/连接监控) →
一次请求 N+1 条 → 找到循环查询的代码 → 改批量
```

### 【分步排查】
**Step 1 · 对照体验**
<details><summary>实测输出</summary>

```json
// 病灶版 mode=n+1
{"mode":"n+1","users":500,"ordersFetched":4947,"sqlCount":501,"costMs":250}
//                                            ↑ 501 条 SQL     ↑ 250ms

// 修复版 mode=batch
{"mode":"batch","users":500,"ordersFetched":4947,"sqlCount":2,"costMs":25}
//                                            ↑ 2 条 SQL      ↑ 25ms
```
本机 loopback 网络往返≈0.2ms/条，501 条才 250ms；**生产跨机房 1~3ms/条时，
同样代码就是 1~2s**——N+1 的伤害与网络延迟成正比。
</details>

**Step 2 · 让 SQL 刷屏可见**：触发场景后（verbose 已开），应用日志实时输出
`[SQL #317] 1 ms | SELECT * FROM user_orders WHERE user_id=...` ——
肉眼确认「接口没死循环，是 SQL 在一条条跑」。

### 【根因】
先查 500 个用户，再**循环**逐个查订单：1 + N 条 SQL。ORM（JPA 的懒加载、
MyBatis 嵌套 select）是 N+1 的高发区——框架替你写的循环最容易忽视。

### 【修复对比】
```java
// ❌ N+1
List<User> users = userDao.findUsers(limit);
for (User u : users) {
    u.setOrders(orderDao.findByUser(u.getId()));   // 循环内逐条查询
}

// ✅ 两条 SQL 批量拿全, 内存归并
List<User> users = userDao.findUsers(limit);
Map<Integer, List<Order>> byUser = orderDao.findByUserIds(ids)   // WHERE user_id IN (...)
        .stream().collect(groupingBy(Order::getUserId));
users.forEach(u -> u.setOrders(byUser.getOrDefault(u.getId(), List.of())));
// JPA 对应: @EntityGraph / JOIN FETCH; MyBAP: 嵌套 resultMap(一次JOIN) 优于嵌套 select
```

### 【预防】
- SQL 执行次数监控（Druid/p6spy 统计「每请求 SQL 数」，突增即报警）；
- Code review 盯紧「循环体内出现 DAO 调用」；
- ORM 懒加载禁止出现在循环与序列化路径。

### ⭐ Arthas
```
trace com.lab.troubleshoot.repository.LabRepository findOrdersByUserIndexed '#cost>1' -n 20
# 每次调用虽快, 但 trace 的调用次数计数(N 次调用)直接暴露 N+1
watch com.lab.troubleshoot.web.OrderController topSpenders '{params,#this}' -x 1 -n 1
```

## 场景 14 · 慢外部依赖：无超时拖垮全站

**触发**：`POST /api/faults/slow-external-no-timeout/trigger`（25 个无超时 caller 打内置慢下游）
**对照体验**：
```bash
curl -w '%{http_code} %{time_total}s\n' -o /dev/null http://localhost:8080/api/payment/no-timeout   # hang 3s+
curl -w '%{http_code} %{time_total}s\n' -o /dev/null http://localhost:8080/api/payment/with-timeout # 503 快速失败
```

### 【模拟告警】
> 【P0告警】全站接口 P99 3.4s，Tomcat 线程池打满（busy 50/50）；
> 下游 payment-svc P99 从 45ms 恶化至 3s —— 疑似级联故障

### 【第0现场 · 可观测性视角】
- 拓扑：**下游服务先变红**，上游随后（因果顺序在拓扑/时间线上非常清晰）；
- 链路：本服务 Span 不慢，慢的是下游 Span —— 但上游线程被占满的连锁反应
  表现为「本服务全接口劣化」；
- 线程指标：Tomcat busy 线程数贴顶 + 大量请求排队 —— 级联故障的标准三联。

### 【定位路线图】
```
ping 仍快(进程没死) → jstack 看 Tomcat 线程在等什么 → 一排 socketRead0 +
调用栈指向同一下游 → 观测拓扑确认该下游 RT 恶化 → 检查 HTTP 客户端配置(无超时!)
```

### 【分步排查】
**Step 1 · 分层**：`curl http://localhost:8080/api/health/ping` → 2ms（实测 0.002s）
进程健康 → 不是 GC/死锁 → 是「线程被占满」或特定链路。

**Step 2 · 看线程在等什么**：`jstack <pid> | grep -A 8 'http-nio-8080-exec' | head -20`
<details><summary>实测特征</summary>

```
"http-nio-8080-exec-5" ... RUNNABLE
	at java.base@21.0.11/java.net.SocketInputStream.socketRead0(Native Method)   ← 挂在读 socket
	...java.net.Socket$SocketInputStream.read
	...org.springframework.http.client...SimpleBufferingClientHttpRequestexecute
	...PaymentDemoController.payNoTimeout(...)    ← 业务帧指向支付调用
```
多个 exec 线程**同样的栈** + 观测系统里下游 RT 恶化 = 无超时等待下游的铁证。
</details>

**Step 3 · 对照实验**（本场景内置）：with-timeout 版同条件下 0.5s 快速失败（实测 503/0.53s），
no-timeout 版 3.0s+ —— 一行配置的差距用数据说话。

### 【根因】
`RestTemplate` 默认**不设超时**（connect/read 无限等待）。下游从 50ms 恶化到 3s，
每个请求挂 3 个 Tomcat 线程干等，线程池打满殃及全站。

### 【修复对比】
```java
// ❌ 默认构造 = 无超时
RestTemplate rt = new RestTemplate();

// ✅ 超时三件套 + 熔断兜底
SimpleClientHttpRequestFactory f = new SimpleClientHttpRequestFactory();
f.setConnectTimeout(500);   // 建连 500ms
f.setReadTimeout(500);      // 读响应 500ms —— 必须显式设置!
RestTemplate rt = new RestTemplate(f);
// 生产再叠加 Resilience4j 熔断: 下游错误率>50% 时直接快速失败, 半开探测恢复
```

### 【预防】
- HTTP 客户端超时是**上线 checklist 必选项**（连接/读/总超时分别评审）；
- 熔断器常态化（Sentinel/Resilience4j），核心链路对弱依赖做降级；
- 全站接口挂但 ping 快 → 第一反应查下游与线程池，而不是自己的业务代码。

### ⭐ Arthas
```
thread --state RUNNABLE | grep -A 5 socketRead    # 成排 socketRead 等待
trace com.lab.troubleshoot.web.PaymentDemoController '*' '#cost>1000'   # 慢在外部调用段
```

## 场景 15 · 锁竞争：锁内做慢 IO

**触发**：`POST /api/faults/slow-lock-contention/trigger`（40 个争抢线程）
**体验**：`curl http://localhost:8080/api/inventory/deduct`（排队恶化）

### 【模拟告警】
> 【P1告警】/api/inventory/deduct P99 8.2s（正常 2.1s），随并发升高**线性**恶化；
> 线程 dump 40+ 线程 BLOCKED 等待同一 monitor

### 【第0现场 · 可观测性视角】
- 指标：单接口 RT 随并发**线性**恶化（无外部依赖变化、无 GC 异常）——
  「RT/并发」斜率突变是锁竞争的指纹；
- 链路：Span 慢在自身（无下游慢 Span、无 DB 慢 Span）；
- 线程指标：BLOCKED 状态线程数与并发数同步（若有线程状态监控）。

### 【定位路线图】
```
jstack 统计 BLOCKED 数量 → 全部 waiting to lock 同一个地址 <0x...> →
看持锁线程(owner)在锁内做什么(sleep/socketRead = 锁内慢IO) → 缩小锁范围
```

### 【分步排查】
**Step 1 · 数阻塞**：`jstack <pid> | grep -c 'BLOCKED'` →（实测 39）
**Step 2 · 看阻塞现场**：
<details><summary>实测输出</summary>

```
"lock-contender" #277 ... BLOCKED (on object monitor)
	at com.lab.troubleshoot.service.InventoryService.deductWithWideLock(InventoryService.java:34)
	- waiting to lock <0x000000016ec7f578> (a com.lab.troubleshoot.service InventoryService)
	                                                                                     ↑ 全员等同一把锁
```
再找 owner：搜 `locked <0x000000016ec7f578>`，它的栈是 `Thread.sleep` ——
**持锁者在锁内睡觉**，其他 39 个排队。判决完成。
</details>

### 【根因】
`synchronized` 方法内做 2s 慢操作（模拟锁内 RPC）：吞吐被锁串行化，
理论 500/s 的接口变成 1/2s = 0.5/s。

### 【修复对比】
```java
// ❌ 整个方法上锁, 锁内含 2s 远程调用
public synchronized void deduct(long holdMs) throws InterruptedException {
    rpcCall();            // 2s, 在锁内!
    stock--;              // 真正需要保护的就这一行
}

// ✅ 缩小锁范围: 只锁共享数据修改; 远程调用移出锁外
String plan = rpcCall();                       // ① 锁外做慢 IO(或预取/异步化)
synchronized (this) { applyPlan(plan); }       // ② 锁内只做纯内存计算
// 进一步: CAS/LongAdder/分段锁/库存预扣+异步落库, 按吞吐要求逐级升级
```

### 【预防】
- review 红线：**锁内禁止 IO/RPC/sleep**（锁内代码按纳秒级标准审查）；
- 压测画出「并发-RT」曲线，斜率异常即排查锁；
- 竞争激烈热点考虑 `java.util.concurrent`（ConcurrentHashMap/LongAdder）替代粗锁。

### ⭐ Arthas
```
thread -b     # 直接指出阻塞源头线程与持锁信息(不用手工对锁地址)
thread --state BLOCKED
```

## 场景 16 · 连接池耗尽：慢 SQL 的连锁反应（综合考核 ⭐）

**触发**：`POST /api/faults/slow-db-pool-exhausted/trigger`（6 个连接占坑线程 vs 池上限 2）
**受害体验**：`curl http://localhost:8080/api/order/1`（正常 1~3ms → 秒级排队）

### 【模拟告警】
> 【P0告警】所有 DB 接口批量报错 Connection is not available, request timed out after
> 10000ms；同时段慢查询日志新增 orders 全表扫描记录 —— 疑似连接池耗尽

### 【第0现场 · 可观测性视角】
- 指标：HikariCP 池指标（active 贴顶 = maximumPoolSize、pending 线程数 > 0、
  `connection_acquire_time` 飙升）+ **同期慢 SQL 告警**（因果双证据）；
- 链路：所有 DB 接口 Span 停在「获取连接」阶段（还没走到 SQL）；
- 全站 DB 接口同时挂 + ping 正常 —— 池级/依赖级故障特征。

### 【定位路线图】（综合运用 12/14 的方法）
```
ping 快 → jstack: 受害线程停在 HikariPool.getConnection(不是 SQL!) →
连接池指标 active=2/2 满载 → 谁占着连接? → 慢查询日志/DB processlist
→ 全表扫描慢 SQL 长期持有连接 → 连锁: 慢SQL → 连接占满 → 全站DB接口挂
```

### 【分步排查】
**Step 1 · 受害接口计时**：`time curl -m 15 http://localhost:8080/api/order/1`
<details><summary>实测输出</summary>

```
$ curl http://localhost:8080/api/order/1
{"order_id":1,...,"costMs":1013}    ← 平时 1~3ms, 现在 1s+(8并发实测≈8s 排队)
real  0m1.028s
```
8 个并发实测全部 ~8s（排队等连接）；并发更大时会触发
`SQLTransientConnectionException ... timed out after 10000ms`（connection-timeout）。
</details>

**Step 2 · 受害线程栈（决定性证据）**
<details><summary>实测 jstack</summary>

```
"http-nio-8080-exec-3" ... WAITING
	at ...SynchronousQueue.poll(SynchronousQueue.java:338)
	at com.zaxxer.hikari.util.ConcurrentBag.borrow(ConcurrentBag.java:151)
	at com.zaxxer.hikari.pool.HikariPool.getConnection(HikariPool.java:162)   ← 停在等连接!
	at ...JdbcTemplate.query(...)
	... OrderController.byId(...)
```
业务线程没在跑 SQL、也没在等下游 —— 它在**等连接**。这是与场景 12/14 的分水岭。
</details>

**Step 3 · 找占坑者**：DB 侧 `SHOW PROCESSLIST`（占坑的 SLEEP/慢查询一目了然）；
应用侧看慢查询日志（场景 12 的告警同期出现）。

### 【根因链】（多因一果，综合考核的意义）
```
慢 SQL 全表扫描(场景12的病) → 每条查询占连接 3s+ →
池只有 2 个连接(配置病) → 正常毫秒级查询也拿不到连接 → 全站 DB 接口挂
```
单独看每一环都不致命，组合起来就是 P0。

### 【修复】（分层次，先止血再治本）
```yaml
# ① 应急: 扩池(治标, 慢 SQL 还在)
hikari:
  maximum-pool-size: 20        # 经验起点: CPU核数*2 + 磁盘数, 压测校准
```
```sql
-- ② 治本: 干掉慢 SQL(回到场景 12 的索引修复)
CREATE INDEX idx_orders_user_id ON orders(user_id);
```
```java
// ③ 防扩散: 大查询走只读从库/独立小池, 不与在线交易抢连接
```

### 【预防】
- Hikari 指标（active/pending/await）必上监控；池大小写进容量文档；
- 慢 SQL 告警与连接池告警做**关联分析**（本场景的因果就是最常见关联）；
- 大促/新功能上线前评估「最长查询耗时 × 并发 > 池大小」的排队风险。

### ⭐ Arthas
```
thread --state WAITING | grep -B 3 -A 10 HikariPool    # 成排线程等连接
trace com.zaxxer.hikari.pool.HikariPool getConnection '#cost>1000'   # 获取连接耗时
ognl '@com.lab.troubleshoot.config.DatabaseInitializer@...'          # 按需探查配置
```
