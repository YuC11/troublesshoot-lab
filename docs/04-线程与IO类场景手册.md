## 场景 08 · 死锁：双锁交叉获取

**触发**：`POST /api/faults/thread-deadlock/trigger`
**受害体验**：触发后想象 /api/transfer 挂死（演练场以线程 dump 呈现）

### 【模拟告警】
> 【P0告警】/api/transfer 3 分钟成功率跌至 71%，失败全部是网关「等待响应超时」(30s)，
> 无 5xx 无异常日志；Tomcat 工作线程逐步耗尽

### 【第0现场 · 可观测性视角】
- 指标：接口**挂死不报错**（超时是网关给的，不是应用给的）——成功率缓跌 +
  无错误日志的组合非常「死锁」；
- 链路：Trace 停在转账 Span 中间不再推进（线程 PARK 住，Span 不关闭）；
- 线程指标：活跃线程数不变（死锁线程不会退出也不会增加）。

### 【定位路线图】
```
jcmd <pid> Thread.print —— 直接看输出末尾: JVM 自动打印 "Found one Java-level deadlock"
(死锁是少数 JVM 会主动给答案的故障, 不用人工推理)
```

### 【分步排查】
**Step 1**：`./scripts/diagnose.sh`（或直接 `jcmd <pid> Thread.print > /tmp/dump.txt`）

<details><summary>实测输出</summary>

```
Found one Java-level deadlock:
=============================
"transfer-A2B":
  waiting for ownable synchronizer 0x000000016f28a798,
      (a java.util.concurrent.locks.ReentrantLock$NonfairSync),
  which is held by "transfer-B2A"

"transfer-B2A":
  waiting for ownable synchronizer 0x000000016f28a768,
      (a java.util.concurrent.locks.ReentrantLock$NonfairSync),
  which is held by "transfer-A2B"
```
两线程交叉持有/等待 = 死锁判决书。往上翻各自的业务栈帧，找到加锁代码行。
</details>

**Step 2**：浏览器直接看：`http://localhost:8080/actuator/threaddump`（等价 jcmd Thread.print）。

### 【根因】
转账两个方向以**相反顺序**获取两把账户锁。并发理论的最小事故模型照进现实。

### 【修复对比】
```java
// ❌ 锁顺序依赖入参: A→B 与 B→A 并发即死锁
public void transfer(Account from, Account to) {
    synchronized (from) { synchronized (to) { ... } }
}

// ✅ 全局统一加锁顺序(如按账号排序), 或一把锁管一个资源域
public void transfer(Account a, Account b) {
    Account first  = a.id < b.id ? a : b;
    Account second = a.id < b.id ? b : a;
    synchronized (first) { synchronized (second) { ... } }
}
// 破坏死锁四条件之一即可: 破坏"循环等待"最常用(统一顺序);
// tryLock(超时)+回退重试 是另一种(破坏"请求保持")
```

### 【预防】
- 任何「获取第二把锁」的代码必须评审锁顺序；
- 定时任务自动抓 Thread.print 检测 deadlock 段（很多公司有死锁巡检）。

### ⭐ Arthas
```
thread --state BLOCKED   # 死锁伴随的阻塞线程
thread -b                # 一键找出"阻塞源头"线程(生产神技: 不用肉眼分析锁图)
thread <id>              # 看指定线程栈
```

## 场景 09 · 线程池耗尽：垃圾任务拖死业务接口

**触发**：`POST /api/faults/thread-pool-exhausted/trigger`（30 个 60s 垃圾任务）
**受害体验**：`curl http://localhost:8080/api/report/summary`（正常 ~100ms → 10s 超时）

### 【模拟告警】
> 【P0告警】/api/report/* 全线 P99 10s+ 网关超时，但 /api/order/* 完全正常；
> 无 5xx、无异常日志、无 GC 告警

### 【第0现场 · 可观测性视角】
- 指标：**只有部分接口** hang（走该线程池的），其他正常 → 立刻排除进程级故障；
- 链路：报表接口 Span 停在「提交任务后等待结果」；
- 线程指标：若暴露线程池 metrics，可看到 active=core 且 queue 持续增长
  （HikariCP/Tomcat/自建池都建议上报）。

### 【定位路线图】
```
curl /api/health/ping(快!) → 排除进程级 → Thread.print 看"正常接口"的线程在等什么
→ 发现等的是业务线程池的任务 → 池的 worker 都在干嘛(TIMED_WAITING sleep?)
→ 队列里堆的是什么任务(看提交处的栈)
```

### 【分步排查】
**Step 1 · 分层**：`curl -w '%{time_total}\n' -o /dev/null http://localhost:8080/api/health/ping` → 毫秒级返回 = 进程健康。

**Step 2 · 受害接口的栈**：压测受害接口的同时 `jcmd <pid> Thread.print | grep -B 2 -A 15 'http-nio-8080-exec'`
<details><summary>实测要点</summary>

请求线程（Tomcat worker）栈停在等待 Future：
```
"http-nio-8080-exec-3" ... WAITING
	at java.base@21.0.11/java.util.concurrent.FutureTask.get(FutureTask.java:390)
	... ReportController.summary(...)      ← 在等业务池的任务结果
```
再看业务池 worker 在干嘛：
```
"biz-report-worker-1" ... TIMED_WAITING (sleeping)
	at java.base@21.0.11/java.lang.Thread.sleep(Native Method)
	... BizReportPool.submitJunkTask(...)  ← 被 60s 垃圾任务占住!
```
`grep -c 'biz-report-worker'` = 4（全部被占），队列长度看 status 接口（实测 26 个排队）。
</details>

**Step 3 · 状态接口对照**

```bash
curl -s http://localhost:8080/api/faults/thread-pool-exhausted/status
```

返回 `{activeWorkers:4, queueBacklog:26, corePoolSize:4}` —— 队列堆积的量化证据。

### 【根因】
共享线程池（core=max=4、无界队列）被长任务占满；正常任务在队列里排队直到超时。
「故障代码」与「受害接口」不在同一个类里——这就是为什么要看线程 dump 而不是只读自己代码。

### 【修复对比】
```java
// ❌ 一个池混跑长任务和在线任务 + 无界队列
executor = new ThreadPoolExecutor(4, 4, 0, MS, new LinkedBlockingQueue<>());

// ✅ 隔离 + 有界 + 明确拒绝策略
ExecutorService onlinePool  = new ThreadPoolExecutor(8, 8, 0, MS,
        new ArrayBlockingQueue<>(200), new ThreadPoolExecutor.AbortPolicy()); // 在线: 快任务
ExecutorService batchPool  = new ThreadPoolExecutor(2, 2, 0, MS,
        new ArrayBlockingQueue<>(1000), new ThreadPoolExecutor.CallerRunsPolicy()); // 批量: 慢任务
```

### 【预防】
- 在线/离线任务**物理隔离**线程池（资源隔离是稳定性设计第一课）；
- 队列必须有界（无界队列 = OOM 与 hang 的二选一难题）；
- 线程池指标（active/queue/reject）接入监控。

### ⭐ Arthas
```
thread --state TIMED_WAITING   # 找到成批 sleep 的 worker
thread -b                      # 若还有锁等待可直接指认源头
vmtool --action getInstances --className java.util.concurrent.ThreadPoolExecutor --limit 5   # 查看池运行时参数
```

## 场景 10 · 线程泄漏：new Thread 不复用

**触发**：`POST /api/faults/thread-leak/trigger?count=200&intervalMs=20`（快速版）

### 【模拟告警】
> 【P1告警】JVM 线程数 4 小时 220 → 3,140（阈值 1000）持续上探；机器 load 升高但 CPU 总量正常

### 【第0现场 · 可观测性视角】
- 指标：线程数**单调上涨**（`jvm_threads_live_threads`）；每线程 512KB~1MB 栈，
  3 千线程 ≈ 1.5~3GB 虚拟内存 + 调度开销；
- 链路正常（泄漏线程多在 sleep/wait，不影响请求）——纯指标型发现；
- 终局：`unable to create new native thread`（无法再创建线程，一切新请求失败）。

### 【定位路线图】
```
Thread.print 统计线程总数与命名分布 → 找出"同名单调增长"的线程 →
按线程名反查创建处(代码里搜 new Thread(..., "该名字")) → 确认无复用/无退出
```

### 【分步排查】
**Step 1 · 计数与分布**
```bash
jcmd <pid> Thread.print | grep -c '^"'                       # 总数(实测: 224)
jcmd <pid> Thread.print | grep '^"' | sed 's/" \?.*//' | sed 's/"//g' | sort | uniq -c | sort -rn | head
```
<details><summary>实测分布</summary>

```
   200 leaked-worker      ← 名字带序号、数量与「线程数增量」吻合 = 泄漏主体
    37 xnio / undertow ...
    25 Tomcat 熟悉的常驻名
```
规律：**业务命名的线程成百上千** = 应用自己创建且未复用；框架线程数量恒定属正常。
</details>

**Step 2 · 抓一个看栈**

```bash
jcmd <pid> Thread.print | grep -A 8 'leaked-worker-1'
```

栈顶 `Thread.sleep` → 结合创建处代码确认「任务挂起等待且永不退出」。

### 【根因】
每个任务 `new Thread(...)` 且长期阻塞（10 分钟 sleep），无池化、无生命周期管理。

### 【修复对比】
```java
// ❌ 请求级创建线程
new Thread(() -> pushService.push(msg), "push-" + id).start();

// ✅ 复用池 + 守护线程 + 优雅关闭
private static final ExecutorService PUSH_POOL = new ThreadPoolExecutor(
        4, 8, 60, SECONDS, new SynchronousQueue<>(),
        r -> { Thread t = new Thread(r, "push-worker"); t.setDaemon(true); return t; });
PUSH_POOL.execute(() -> pushService.push(msg));
```

### 【预防】
- 规范禁用裸 `new Thread`（review + 静态扫描）；
- 线程必须有名字（无名线程泄漏了都搜不到）；
- 线程数纳入监控告警。

### ⭐ Arthas
```
thread --all | grep -c leaked    # 或 thread -n 大数全列; dashboard 底部线程数实时
```

## 场景 11 · 文件句柄泄漏：Too many open files

**触发**：`POST /api/faults/io-handle-leak/trigger?rate=200&maxHandles=600`（快速版；默认 rate=40、maxHandles=2000，可传更大 `maxHandles` 亲历打满）

### 【模拟告警】
> 【P0告警】突发大量 IOException: Too many open files；MySQL 报 "Can't open file"、
> 新 HTTP 连接被拒 —— 进程 fd 打满

### 【第0现场 · 可观测性视角】
- 指标：进程级 fd 数指标（node_exporter `process_open_fds`）持续上涨逼近
  `ulimit -n`；
- 日志：一切 IO 突然集体报错（DB、HTTP、文件、日志写盘），**同一时刻**爆发——
  「所有依赖同时坏」几乎只有一个解释：本进程 fd 耗尽；
- 与网络故障的区分：换台机器 curl 服务依然能通（已建立的连接不受影响，新建的失败）。

### 【定位路线图】
```
lsof -p <pid> | wc -l 看总数(对照 ulimit -n) →
lsof -p <pid> | awk '{print $NF}' | sort | uniq -c | sort -rn | head
→ 同一个文件被打开 N 千次 = 泄漏文件 → 反查打开处代码(没 close)
```

### 【分步排查】

**Step 1**：`ulimit -n`（本机常见 2560）与 `lsof -p <pid> | wc -l` 对照。

**Step 2 · 按文件聚合**（泄漏的形状一目了然）：
<details><summary>实测输出</summary>

```
$ lsof -p 31319 | grep handle-leak-probe | wc -l
600          ← 同一个探针文件被打开 600 次!

$ lsof -p 31319 | awk '{print $NF}' | sort | uniq -c | sort -rn | head -3
   639 /Users/yc/Downloads/paper/target/handle-leak-probe.bin
    ...mysql-socket / 日志文件等正常项(各 1~2 个)
```
正常文件 fd 是个位数；**同一文件成百上千 = 它就是泄漏源**。
</details>

**Step 3 · 打满实测**（可选）：`trigger?rate=300&maxHandles=5000` → 演练场会捕获真实的 `FileNotFoundException: Too many open files` 并在 status.error 展示。

### 【根因】
IO 流用完不 close（尤其**异常路径**漏关）——本场景代码故意不用
try-with-resources / `@Cleanup`，让事故先发生。

### 【修复对比】
```java
// ❌ 手动 close: 异常提前 return 就漏了
InputStream in = new FileInputStream(f);
byte[] head = in.readNBytes(16);
if (head.length < 16) return null;   ← 这里 return, in 永远没关
in.close();

// ✅ try-with-resources: 任何路径都保证关闭
try (InputStream in = new FileInputStream(f)) {
    ...
}   // 自动 close; Lombok @Cleanup 是等价的字节码级方案
```

### 【预防】
- 强制 try-with-resources（静态扫描 Sonar 规则 S2082 类）；
- fd 使用率监控（80% 告警）；
- systemd/launchd 服务显式提高 `LimitNOFILE`（治标兜底，不替代修复）。

### ⭐ Arthas
```
dashboard              # 线程/内存正常 —— fd 问题 JVM 内面板看不到, 用 lsof
vmtool --action getInstances --className java.io.FileInputStream --limit 3
                        # 数一数流实例(配合 ognl 可进一步过滤)
```
