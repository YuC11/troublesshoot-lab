## 场景 01 · 堆内存 OOM：无界缓存

**触发**：`POST /api/faults/oom-heap/trigger`（默认温和模式 180MB）
**crash 模式**：`POST /api/faults/oom-heap/trigger?mode=crash`（真 OOM + 自动 dump）

### 【模拟告警】
> 【P0告警】troubleboot-lab(10.0.0.11:8080) 堆内存使用率 93%（阈值85%），Old 区回收后不下降，
> 5 分钟内 Full GC 12 次，接口 P99 从 45ms 升至 3.2s

### 【第0现场 · 可观测性视角】
- Grafana/SkyWalking JVM 大盘：堆使用曲线**爬坡**且回收后基线逐日上移（vs 正常锯齿）；
  FGC 次数陡增；进程存活但 RT 全线恶化。
- 链路：各接口 Span 普遍变长（GC 停顿拖累所有请求），无单一慢点 → 指向进程级资源问题。
- 结论：范围已缩到「本实例 JVM 堆」，带着「谁占着堆不放」的假设登机。

### 【定位路线图】（JDK 9+ 以 jcmd 为正统；JDK 8 老服务器对应命令见 01 手册 §3.2 演进表）
```
jcmd GC.heap_info 快照 + jstat 看趋势(老年代回收后不降?) →
jcmd GC.class_histogram 找对象大头 →
jcmd GC.run 前后对照(区分泄漏vs缓存) → crash模式看dump → 读代码找引用链
```

### 【分步排查】（先自己想，再展开对照）

**Step 1 · 堆快照 + 老年代趋势**
```bash
jcmd <pid> GC.heap_info                 # 一屏快照: 堆各区 + Metaspace
jstat -gcutil <pid> 1000 10             # 趋势观察(jcmd 无流式采样, jstat 仍是正解)
```
<details><summary>GC.heap_info 实测输出（触发场景后）</summary>

```
 garbage-first heap   total 262144K, used 234246K ...
  region size 1024K, 14 young (14336K), 0 survivors (0K)
 Metaspace       used 45948K, committed 46784K, reserved 131072K
```
used 逼近 total = 堆将满；对照 jstat 趋势：
```
  S0    S1    E      O      M     CCS   YGC   YGCT   FGC   FGCT   CGC  ...
  -    0.0  100.0  73.2  98.1  93.0   412  0.812    3   0.905    2
  -    0.0  100.0  87.5  98.1  93.0   455  0.901    4   1.204    2   ← O 列只涨不降
```
O = 老年代使用率。**多次采样 O 持续 >85% 且 FGC 后不回落** = 堆被强引用占住
（M 列为何也在 98？见 01 总纲 §3.4 口径陷阱）。
</details>

**Step 2 · 谁占的**：`jcmd <pid> GC.class_histogram | head -10`
<details><summary>实测输出</summary>

```
 num     #instances         #bytes  class name (module)
   1:         68252      193504176  [B (java.base@21.0.11)    ← byte[] 占 185MB，最大嫌疑
   2:         66085        1586040  java.lang.String (java.base@21.0.11)
```
`[B` 是 byte[] 的 JVM 签名。数量 6 万+、总量随时间增长 → 业务在囤字节数组。
（JDK 8 老服务器：`jcmd <pid> GC.class_histogram` 等价）
</details>

**Step 3 · 泄漏还是缓存**：`jcmd <pid> GC.run` 后重复 Step 2 —— 清不掉 = 强引用泄漏。

**Step 4 · crash 模式的铁证**：`ls -lh dumps/`

（crash 触发后场景会**自动清空自愈**并转 ERROR 状态——OOM 杀死的是线程不是进程；
自愈代码顺序的纪律见场景 02 Step 4，与生产"OOM 后必须重启"不冲突）
<details><summary>实测</summary>

```
-rw-------  1 yc  staff   40M  java_pid31319.hprof
```
`-XX:+HeapDumpOnOutOfMemoryError` 在 OOM 瞬间自动落盘（运行中也可手动
`jcmd <pid> GC.heap_dump /tmp/heap.hprof`，⚠️ STW 重操作）。用 MAT（Eclipse Memory
Analyzer）打开 → Dominator Tree → 按 Retained Heap 排序 → 泄漏对象被谁引用，
一路 GC Roots 点下去，答案通常是某个 static Map/List。间歇性泄漏追不到现场时
上 JFR：`jcmd <pid> JFR.start settings=profile duration=120s filename=rec.jfr`，
JMC 里看对象分配栈（现代低开销「黑匣子」）。
</details>

**Step 5 · 停止恢复验证与「GC 惰性」（重要认知）**

执行 `POST /api/faults/oom-heap/stop` 后立刻 `jstat -gcutil`，**预期 O 列立即回落**
（stop 内置"清空引用 + 显式 Full GC"，日志打印 `堆 X MB → Y MB` 前后对比；
机制正主见 01 总纲 §4.1——这里只放实测案例）。

<details><summary>实测案例：为什么引用清空后堆可能不降</summary>

停止后应用几乎零分配 → Eden 装不满 → 不触发 Young GC → G1 不做 IHOP 检查 →
并发标记周期不启动 → 死掉的 humongous 对象（10MB byte[] 超过 region 一半大小，
直接分配在老年代）长期占着 O≈100%。实测（旧版本无内置 GC 时）：停止后观察 60 秒，
`YGC/CGC` 计数**全程冻结**、只有 E 缓慢爬升——没有任何 GC 发生。

此时一条命令立见分晓：

```bash
jcmd <pid> GC.run          # 显式触发
jcmd <pid> GC.heap_info    # used 244MB → 23MB, O 99.89% → 22%
```
</details>

### 【根因】
static 集合当缓存只进不出（`HeapOomScenario.unboundedCache`）。

### 【修复对比】
```java
// ❌ 故障代码：无界缓存
private static final List<byte[]> CACHE = new ArrayList<>();
public void put(byte[] data) { CACHE.add(data); }

// ✅ 修复：有界 + 过期（三选一按场景）
private static final Map<String, byte[]> CACHE =
        Caffeine.newBuilder().maximumWeight(64L << 20)   // 上限 64MB
                .weigher((k, v) -> v.length)
                .expireAfterWrite(10, TimeUnit.MINUTES)  // 过期兜底
                .build();
// 大对象查询改分页/流式；批量导出走文件而非内存聚合
```

### 【预防】
- 缓存必须有界（Caffeine maximumSize/maximumWeight）+ 过期策略；
- 压测覆盖「数据量 10 倍增长」场景；OOM 前的堆基线上移告警（比 OOM 告警提前数天）。

### ⭐ Arthas 一键定位
```
dashboard                       # 堆/Metaspace 实时 + 线程 Top
heapdump --live /tmp/heap.hprof # 只dump存活对象, 拖进 MAT
vmtool --action getInstances --className java.util.ArrayList --limit 3   # 看大集合实例
```

## 场景 02 · Metaspace OOM：动态类/类加载器泄漏

**触发**：`POST /api/faults/oom-metaspace/trigger`（温和 4000 个加载器）

**crash 模式**：`?mode=crash` → 真 `OutOfMemoryError: Metaspace`（自动自愈，见 Step 4）

### 【模拟告警】
> 【P1告警】JVM 已加载类数 1 小时 8,412 → 41,308，Metaspace 92.8MB/96MB

### 【第0现场 · 可观测性视角】
- 指标：`jvm_classes_loaded` **单调上涨不回落**是最强信号（正常服务类数恒定）；
  Metaspace 使用率逼近 `-XX:MaxMetaspaceSize`。
- 日志：常见于 Groovy/表达式引擎/动态代理业务（规则引擎、报表模板）上线后。
- 链路无异常（类加载不直接影响 RT），靠指标告警发现。

### 【定位路线图】
```
jcmd GC.heap_info 看 Metaspace committed 逼近 MaxMetaspaceSize(撞墙口径) →
确认类数上涨 (jcmd VM.metaspace / 控制台 loadedClassCount) → jcmd GC.class_histogram
看不到元数据(堆直方图无大头, 这是与堆OOM的分水岭) → 查代码: 谁在 defineClass
```

### 【分步排查】

**Step 1 · Metaspace 真实余量**

```bash
jcmd <pid> GC.heap_info | grep -i metaspace
```

```
 Metaspace       used 47432K, committed 68352K, reserved 147456K   ← 温和4000个时实测
```

> **⚠️ 撞墙的是 committed，不是 used**：`-XX:MaxMetaspaceSize=96m`（本演练 98304K）限制的是
> committed。海量小类加载器场景下两者差距巨大——JEP 387 弹性元空间给每个加载器独立 arena，
> **每个加载器 committed ≈ 6KB ≈ 6.7× 实际用量(0.9KB)**。裸 JVM 64m 上限实验：10,765 个
> 加载器时 used 仅 10.4MB，committed 恰 65,536KB 触发 OOM（口径陷阱正主见 01 总纲 §3.4）。
> 趋势观察用 `jstat -gcmetacapacity <pid> 1000 5`（**MC=committed 正是撞墙口径**，随泄漏增长）。

**Step 2 · 确认类数上涨**

```bash
jcmd <pid> VM.metaspace | head
```

看 Loaded classes 总数与 committed 细分——类数**单调上涨不回落**是类泄漏的最强信号。

**Step 3 · 堆直方图排除堆泄漏**

```bash
jcmd <pid> GC.class_histogram | head -5
```

**没有异常大头**（区别于场景01，这是与堆 OOM 的分水岭），但控制台 `/api/metrics` 的
loadedClassCount 持续上涨（实测从 9775 → 13277）。

**Step 4 · 停止恢复验证**

```bash
curl -X POST http://localhost:8080/api/faults/oom-metaspace/stop
```

仪表盘应立即回落（stop 内置"释放引用 + Full GC 类卸载"，日志打印
`Metaspace X KB → Y KB, 已加载类 N → M`）。
温和模式(默认 4000 加载器)实测：used 42.1 → 46.6 → 42.9（+4.5MB，一位小数肉眼可见），
committed 同期 44 → 68MB；**已加载类数** 9.7k → 13.8k → 9.8k 是同步旁证（stop 日志
`Metaspace 47732 KB → 43956 KB, 已加载类 13785 → 9787`）。场景内置 committed 80MB
安全水位刹车，即便 `?targetLoaders=` 要得过大也只会提前停手、不会撞墙。

**crash 模式**（`?mode=crash`）：真实逼近 96m 上限 → `OutOfMemoryError: Metaspace` +
自动落 dump → **场景自动自愈**（清引用 + GC 卸载死类）并转入 ERROR 状态
（控制台红色原因可读）→ 点停止即复位。自愈代码的顺序本身就是教学点：

```java
// ❌ 反模式(本演练台真实冻死事故的根因): catch 里先拼字符串记账
//    字符串拼接的 invokedynamic 首次链接要在仍被打满的元空间里定义新类
//    → 二次 OOM 从 catch 内抛出 → clear() 永远执行不到 → 加载器被永久持有
//    → 所有 HTTP 线程连环 OOM, 停止接口不可达, 连 SIGTERM 都无法分发
catch (OutOfMemoryError oom) {
    markDamaged("OOM: " + oom.getMessage());   // ← 二次 OOM 点
    loaders.clear();                            // ← 永远到不了
}
// ✅ OOM 后的错误处理纪律: 先做零分配的救命动作, 全部成功后才能记账
catch (OutOfMemoryError oom) {
    oomOccurred = true;      // 基本类型/引用赋值, 不分配
    loaders.clear();         // 清引用
    System.gc();             // 卸载死类, 腾出元空间
    try { markDamaged(...); log.error(...); } catch (Throwable ignored) {}  // 记账兜底
}
```

类卸载的两个前提——加载器不可达 + 发生 GC——机制见 01 总纲 §4.1（GC 惰性）。

### 【根因】
每个请求/任务 new 一个 ClassLoader 去 defineClass（动态代理、脚本编译），
加载器被持有 → 类永不卸载（类卸载条件：**类加载器本身可回收**）。

### 【修复对比】
```java
// ❌ 每次都 new 加载器编译脚本 → 类无限增长
Class<?> c = new GroovyClassLoader().parseClass(script);

// ✅ 缓存编译结果：脚本内容 hash → Class 复用；必须换加载器时先 close
private static final Map<String, Class<?>> COMPILED = new ConcurrentHashMap<>();
Class<?> c = COMPILED.computeIfAbsent(sha256(script), this::compileOnce);
```

### 【预防】
- MaxMetaspaceSize 显式设置（默认无上限，会吃光内存才倒下）；
- 监控 `loaded class count` 增速；动态类技术选型评审时问「类会不会被卸载」。

### ⭐ Arthas
```
dashboard            # Metaspace 使用实时可见
sc -d *MetaspaceMarker   # 查类详情; sm 看方法; jad 反编译确认动态生成的类
```

## 场景 03 · ThreadLocal 内存泄漏（隐性，无 OOM）

**触发**：`POST /api/faults/leak-threadlocal/trigger?rounds=4`（每轮 4 线程 × 10MB）

### 【模拟告警】
> 【P1告警】堆内存锯齿上移（Old 区 GC 后基线每 30min +18MB），无 OOM 但 Full GC
> 从 2 次/天 升至 9 次/小时，疑似内存泄漏

### 【第0现场 · 可观测性视角】
- 指标：堆基线**缓慢**上移（比场景 01 温和得多）+ FGC 频率趋势上涨；
- 链路/日志无异常 —— 这类泄漏靠「趋势告警」而非「故障告警」发现；
- 排查时机：低峰期，因为要主动触发 GC 做对照。

### 【定位路线图】
```
jstat 确认回收后不降 → jcmd GC.class_histogram 看 byte[] 大头 → jcmd GC.run 再看(仍不降!)
→ 泄漏但无业务引用 → 怀疑隐藏持有者: ThreadLocal/线程池 → dump 看引用链
(MAT: Thread.threadLocals → ThreadLocalMap.Entry[].value)
```

### 【分步排查】

**Step 1 · 触发并确认「GC 后不降」**

```bash
curl -X POST 'http://localhost:8080/api/faults/leak-threadlocal/trigger?rounds=4'
jcmd <pid> GC.run && sleep 2 && jstat -gcutil <pid>
```

预期：强制 GC 后 **O 列（老年代）仍不回落**——GC 真的发生了（YGC/FGC 计数在涨），
但回收不掉，这就是泄漏实锤（区别于场景 01 停止后的「GC 惰性」：那里是 GC 根本没发生）。

<details><summary>为什么 GC 救不了</summary>

ThreadLocalMap 的 Entry.key 是**弱引用**（GC 会清掉 key），但 **value 是强引用**，
且 Entry 挂在**线程对象**上。线程池的线程常驻不死 → value 永远可达 → 泄漏。
只有线程死亡或同线程后续 set/remove 触发 stale entry 清理才会释放。
</details>

> 对照场景 01 的「GC 惰性」框：这里的 GC.run 是**诊断手段**（GC 后不降 = 泄漏证据）；
> 而场景 01 停止后不降是**回收未发生**（清了引用但没 GC 发生）。同一个命令两种用途。

**Step 2 · 堆里谁大**

```bash
jcmd <pid> GC.class_histogram | head -8
```

预期：`byte[]` 高居榜首（每轮 4 线程 × 10MB）。但直方图只回答「谁大」，
不回答「谁持有」——继续 Step 3。

**Step 3 · dump 找持有链**

```bash
jcmd <pid> GC.heap_dump /tmp/tl-leak.hprof   # ⚠️ STW 重操作, 生产放低峰期
```

用 MAT（Eclipse Memory Analyzer）打开 → Histogram → 右键 `byte[]` →
List objects (with incoming references) → `Path to GC Roots (exclude weak/soft references)`，
预期引用链（示意）：

```
Thread @ 0x... "tl-leak-pool-N"
 └─ threadLocals → ThreadLocal$ThreadLocalMap
     └─ Entry[].value
         └─ byte[10485760]
```

持有者是**线程**而非任何业务对象——这就是答案。

**Step 4 · 停止恢复验证**

```bash
curl -X POST http://localhost:8080/api/faults/leak-threadlocal/stop
```

stop 内置"清空泄漏 ThreadLocal + 显式 GC"（契约见 01 总纲 §4.3），仪表盘堆应立即回落。

### 【根因】
线程池常驻线程上 `ThreadLocal.set(大对象)` 后不 `remove()`（`ThreadLocalLeakScenario`）。

### 【修复对比】
```java
// ❌ 任务结束不清
tl.set(new BigContext());
doBusiness();

// ✅ finally 必清（或 try-with-resources 的 ThreadLocal 模式）
try {
    tl.set(new BigContext());
    doBusiness();
} finally {
    tl.remove();   // 一行，但线上事故里它价值一辆车
}
```

### 【预防】
- 规范：ThreadLocal 与 finally/remove 成对出现（代码评审 checklist 项）；
- 大对象优先考虑方法参数传递而非 ThreadLocal；
- 线程池场景审计：入池任务用完的 ThreadLocal 是否清理。

### ⭐ Arthas
```
heapdump --live /tmp/h.hprof 后用 MAT 搜 ThreadLocalMap
vmtool --action getInstances --className java.lang.ThreadLocal --limit 10  # 看实例数
```

## 场景 04 · GC 风暴：内存不足伪装 CPU 高 ⭐误诊之王

**触发**：`POST /api/faults/gc-storm/trigger`（填 170MB 老年代 + 2 个分配风暴线程）

### 【模拟告警】
> 【P0告警】CPU 97%（阈值85%），但 QPS 无明显上涨；接口 RT 普涨、无单接口异常

### 【第0现场 · 可观测性视角】
- 指标：CPU 高 + **GC 耗时/频率同步飙升**（`jvm_gc_pause_seconds`）；
- 链路：RT 整体抖动但**无慢 Span**（耗在 GC 停顿，不在任何业务环节）；
- 「CPU 高 + 无慢Span + GC 告警」三件套出现 → 直接跳过业务代码排查。

### 【定位路线图】—— 场景 05 的镜像
```
top -Hp 找高CPU线程 → Thread.print 查无此 nid(!) → 线程名是 "GC Thread#N"/
"C2 CompilerThre" → 确认是 GC 线程在吃 CPU → jstat -gcutil 看 FGC 狂涨
→ 转入内存排查(场景01/03 的路线) 找出堆被谁占住
```

### 【分步排查】
**Step 1 · 找高 CPU 线程**

```bash
top -Hp <pid>    # Linux（生产标准）
jcmd <pid> Thread.print | sed -E 's/^"([^"]+)".*cpu=([0-9.]+)ms.*/\2 \1/' | sort -rn | head -5   # 🍎 macOS
```

<details><summary>实测关键现象（Linux top 视角示意）</summary>

```
  PID  USER  %CPU  COMMAND           ← Linux: 高CPU线程名是 GC Thread#N
 8423  app  99.7  "GC Thread#5"      ← 不是你的业务线程!
 8424  app  98.2  "GC Thread#2"
 8425  app  96.8  "G1 Conc Refinement"
```
拿这些 ID 去 Thread.print 输出里 grep —— **查无此线程**：GC 线程是 JVM 内部线程，
不出现在 Java 线程 dump 的业务栈里。「找不到」本身就是最重要的线索。
</details>

**Step 2 · jstat 定罪**

```bash
jstat -gcutil <pid> 1000 5
```

<details><summary>实测输出（触发 6 秒后）</summary>

```
  S0    S1    E      O      M     CCS    YGC    YGCT    FGC    FGCT     GCT
  -    0.2   1.5   95.1   97.9  93.0   2600   1.747   1586   14.652   16.404
   ↑O=95%               ↑YGC=2600      ↑FGC=1586 次且 FGCT 持续累积
```
FGC 每 10 秒 +几十次、Old 恒定 95%+ = Full GC 空转（收不出空间，反复全收集）。
实测进程 CPU 391%（GC 线程并行工作）。
</details>

### 【根因】
长生命周期对象占满老年代（+ 分配风暴）→ G1 反复 Full GC → GC 线程吃满 CPU。
**CPU 是症状，内存才是病根。**

### 【修复】
- 应急：扩堆 `-Xmx` 可立刻缓解（有富余机器内存时）；
- 治本：按场景 01/03 路线找出老年代大头清理掉；
- 若是「堆确实太小」：重算容量（活跃数据 × 2~3 倍），并审视分配速率。

### 【预防】
- 告警把 CPU 与 GC 指标放同一块大盘（同屏可见防误诊）；
- 容量规划评审：堆 < 存活数据 × 2 是事故预备。

## 场景 17 · 堆外内存 OOM：Direct Memory 泄漏

**触发**：`POST /api/faults/oom-direct-memory/trigger`（温和 48 块 × 1MB，`-XX:MaxDirectMemorySize=64m`）
**crash 模式**：`?mode=crash` → 真 `OutOfMemoryError: Direct buffer memory`（自动自愈）

### 【模拟告警】
> 【P1告警】troubleboot-lab 进程 RSS 3.2GB 但堆只用 800MB；NIO 直接内存 61MB/64MB，
> BufferPool direct_count 单调上涨

### 【第0现场 · 可观测性视角】
- 指标：`jvm_buffer_memory_used_bytes{pool="direct"}` 单调上涨；
  进程 RSS 与堆使用**严重背离**（堆平稳、RSS 爬坡）——这是堆外泄漏的指纹；
- 链路/日志无异常（分配动作不报错）——靠 BufferPool 指标或 OOM 才发现。

### 【定位路线图】
```
RSS 高但堆平稳(堆外嫌疑) → jcmd GC.heap_info 排除堆/Metaspace →
jcmd VM.native_memory summary 看 Internal/Other(NMT 需 -XX:NativeMemoryTracking=summary) →
jcmd GC.class_histogram 排除堆内大头(堆外对象不占堆!) → 查代码: 谁在 allocateDirect 不释放
```

### 【分步排查】
**Step 1 · 确认「堆外嫌疑」**

```bash
jcmd <pid> GC.heap_info
```
预期：堆 used 不高——排除堆与 Metaspace 后，RSS 与堆的缺口指向堆外。

**Step 2 · 直接内存池水位**

```bash
jcmd <pid> VM.native_memory summary | grep -A 3 Internal
```
NMT 视角（lab.sh 已开 `-XX:NativeMemoryTracking=summary`）；控制台
`/api/faults/oom-direct-memory/status` 的 `directUsedMb/directMaxMb` 是同源简化版
（BufferPoolMXBean）。温和 48 块实测：direct 0.1 → 48.1 → **0 MB**（stop 日志 `已释放 48 块堆外内存并触发 GC(Cleaner 回收): direct 48 MB → 0 MB`）。

**Step 3 · 堆直方图反证**

```bash
jcmd <pid> GC.class_histogram | head -5
```
预期：**没有异常大头**——DirectByteBuffer 的对象壳在堆里只有几十字节，
真身（native 内存）堆直方图看不见。这是与场景 01 的分水岭，也是
「堆 OOM 排查法在此失效」的教学点。

**Step 4 · 停止恢复验证**

```bash
curl -X POST http://localhost:8080/api/faults/oom-direct-memory/stop
```
stop 内置「清引用 + System.gc()」：**堆外内存的释放条件 = DirectByteBuffer 不可达 +
一次真实的 GC 执行 Cleaner**（与类卸载同款纪律，见 01 §4.1/§4.3）——
引用清空后不 GC，BufferPool 水位纹丝不动。crash 模式 OOM 后自动自愈转 ERROR。

### 【根因】
`ByteBuffer.allocateDirect(...)` 分配的堆外内存不经 GC 管辖（只受
`-XX:MaxDirectMemorySize` 限制），持有引用不释放 → 打满后新分配抛
`OutOfMemoryError: Direct buffer memory`。高频成因：Netty ByteBuf 未 release、
DirectBuffer 池无界、`FileChannel.map` 的 MappedByteBuffer 缓存。

### 【修复对比】
```java
// ❌ 分配后不释放(依赖 GC, 而 GC 恰恰不确定何时来)
ByteBuffer buf = ByteBuffer.allocateDirect(1024 * 1024);
cache.add(buf);   // 无界持有

// ✅ ① 有界池化(Netty PooledByteBufAllocator 自带) ② 用完 release
// ③ 兜底: 容量用 BufferPoolMXBean 监控 + MaxDirectMemorySize 显式设限
```

### 【预防】
- `-XX:MaxDirectMemorySize` 显式设置（默认≈Xmx，容易吃光容器限额）；NMT 常态开启排查期；
- BufferPool direct 指标上监控（used/count 双维）；Netty 项目泄漏检测 `IoLeakAwareByteBuf`。

### ⭐ Arthas
```

vmtool --action getInstances --className java.nio.DirectByteBuffer --limit 5
```

## 附录 · 容器内存模型：为什么「本地好好的，进容器就被 OOMKilled」

### 为什么「本地好好的，进容器就被 OOMKilled」

JVM 进程内存 = 堆 + Metaspace + 线程栈(线程数×Xss) + GC 开销 + 堆外(Direct/Netty) +
JIT 代码缓存。**容器 OOMKilled 看的是 cgroup limit（整个进程），不是 -Xmx**：

```
容器限额 1Gi
├─ -Xmx512m（堆, 只占一半!)
├─ Metaspace ~100m
├─ 线程栈 200线程 × 1m = 200m
├─ Direct/Netty 堆外 ~150m   ← 默认≈Xmx, 是隐藏大头
└─ JIT/GC/符号表 ~80m        → 合计 1.05Gi > 1Gi → 内核 OOMKiller 干掉进程(137)
```

要点：① `java -XX:+PrintFlagsFinal -version | grep MaxHeapSize` 验证容器内实际堆；
② JDK 10+ 默认 `UseContainerSupport`，`-XX:MaxRAMPercentage=70` 按限额比例切堆，
比写死 -Xmx 更稳；③ 留足非堆余量（经验：堆 ≤ 限额 50~70%）；
④ OOMKilled(exit 137) 排查顺序：`kubectl describe pod` 看 OOMKilled → 反推各内存区之和。
