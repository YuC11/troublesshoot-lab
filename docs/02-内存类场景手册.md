# 02 · 内存类场景手册（场景 01~04）

> 排查总纲与工具优先级见 [01 方法论](01-排查方法论与工具优先级.md)。
> 以下命令 `<pid>` 用 `jps -l | grep troubleshoot` 获取（控制台右上角也有实时 PID）。
> 🍎 标注 = macOS 与 Linux 命令差异（Linux 为主）。

> ### 📌 阅读须知（两个高频困惑，正文不再重复解释）
>
> **① jstat 的 M 列 ≈98 不是 Metaspace 要爆**：M = used/**committed**，JDK16+ 弹性元空间
> 让 committed 紧贴 used，常态 90%+——它**不是** used/MaxMetaspaceSize。真实余量看
> `jcmd <pid> GC.heap_info` 的 used 对比上限（本演练 64MB，基线约 45MB ≈ 70%）。
> 场景 01 触发前后 M 都是 98 正是此因（它只动堆）；场景 02 才真正逼近上限。
> 顺带：选项名是 `-gcmetacapacity`，没有 `-gcmetaspace` 这个选项。
>
> **② 引用清空 ≠ 内存释放**：`clear()` 只让对象不可达，jstat 的 O 列要等一次真实的老年代
> 回收才回落；停止后应用几乎零分配，G1 可能长时间不触发回收（实测 YGC/CGC 冻结）。
> 演练场 stop 已内置 System.gc() 让回落立即可见；手动验证用 `jcmd <pid> GC.run`。
> 完整实测案例见场景 01 Step 5。

## 场景 01 · 堆内存 OOM：无界缓存

**触发**：`POST /api/faults/oom-heap/trigger`（默认温和模式 180MB）
**crash 模式**：`POST /api/faults/oom-heap/trigger?mode=crash`（真 OOM + 自动 dump）

### 【模拟告警】
> 【P0告警】troubleboot-lab(10.0.0.11:8080) 堆内存使用率 93%（阈值85%），Old 区回收后不下降，
> 5 分钟内 Full GC 12 次，接口 P99 从 45ms 升至 3.2s

### 【第0现场 · 可观测性视角】
- Grafana/SkyWalking JVM 大盘：堆使用曲线**爬坡**且回收后基线逐日上移（vs 正常锯齿）；
  FGC 次数陡增；进程存活但 RT 全线恶化。
- 链路：各接口 Span 普遍变长（GC 停顿拖累所有请求），无单一慢点 → 指向进程级资源问题。
- 结论：范围已缩到「本实例 JVM 堆」，带着「谁占着堆不放」的假设登机。

### 【定位路线图】（JDK 9+ 以 jcmd 为正统；JDK 8 老服务器对应命令见 01 手册 4.2 演进表）
```
jcmd GC.heap_info 快照 + jstat 看趋势(老年代回收后不降?) →
jcmd GC.class_histogram 找对象大头 →
jcmd GC.run 前后对照(区分泄漏vs缓存) → crash模式看dump → 读代码找引用链
```

### 【分步排查】（先自己想，再展开对照）

**Step 1 · 堆快照 + 老年代趋势**
```bash
jcmd <pid> GC.heap_info                 # 一屏快照: 堆各区 + Metaspace
jstat -gcutil <pid> 1000 10             # 趋势观察(jcmd 无流式采样, jstat 仍是正解)
```
<details><summary>GC.heap_info 实测输出（触发场景后）</summary>

```
 garbage-first heap   total 262144K, used 234246K ...
  region size 1024K, 14 young (14336K), 0 survivors (0K)
 Metaspace       used 45948K, committed 46784K, reserved 131072K
```
used 逼近 total = 堆将满；对照 jstat 趋势：
```
  S0    S1    E      O      M     CCS   YGC   YGCT   FGC   FGCT   CGC  ...
  -    0.0  100.0  73.2  98.1  93.0   412  0.812    3   0.905    2
  -    0.0  100.0  87.5  98.1  93.0   455  0.901    4   1.204    2   ← O 列只涨不降
```
O = 老年代使用率。**多次采样 O 持续 >85% 且 FGC 后不回落** = 堆被强引用占住
（M 列为何也在 98？见顶部「阅读须知」①）。
</details>

**Step 2 · 谁占的**：`jcmd <pid> GC.class_histogram | head -10`
<details><summary>实测输出</summary>

```
 num     #instances         #bytes  class name (module)
   1:         68252      193504176  [B (java.base@21.0.11)    ← byte[] 占 185MB，最大嫌疑
   2:         66085        1586040  java.lang.String (java.base@21.0.11)
```
`[B` 是 byte[] 的 JVM 签名。数量 6 万+、总量随时间增长 → 业务在囤字节数组。
（JDK 8 老服务器：`jcmd <pid> GC.class_histogram` 等价）
</details>

**Step 3 · 泄漏还是缓存**：`jcmd <pid> GC.run` 后重复 Step 2 —— 清不掉 = 强引用泄漏。

**Step 4 · crash 模式的铁证**：`ls -lh dumps/`
<details><summary>实测</summary>

```
-rw-------  1 yc  staff   40M  java_pid31319.hprof
```
`-XX:+HeapDumpOnOutOfMemoryError` 在 OOM 瞬间自动落盘（运行中也可手动
`jcmd <pid> GC.heap_dump /tmp/heap.hprof`，⚠️ STW 重操作）。用 MAT（Eclipse Memory
Analyzer）打开 → Dominator Tree → 按 Retained Heap 排序 → 泄漏对象被谁引用，
一路 GC Roots 点下去，答案通常是某个 static Map/List。间歇性泄漏追不到现场时
上 JFR：`jcmd <pid> JFR.start settings=profile duration=120s filename=rec.jfr`，
JMC 里看对象分配栈（现代低开销「黑匣子」）。
</details>

**Step 5 · 停止恢复验证与「GC 惰性」（重要认知）**

执行 `POST /api/faults/oom-heap/stop` 后立刻 `jstat -gcutil`，**预期 O 列立即回落**
（演练场 stop 内置了"清空引用 + 显式 Full GC"，日志会打印 `堆 X MB → Y MB` 前后对比）。

但如果你在**旧版本**上观察，或生产上删了缓存/集合后盯着监控，很可能看到
**O 高位纹丝不动**——这不是"没释放"，而是 **GC 惰性**：

<details><summary>为什么引用清空后堆不降？（实测案例）</summary>

内存释放要同时满足三个条件：① 对象不可达（clear() 只完成这一步）；
② **JVM 真的执行了一次覆盖老年代的回收**；③ 你在回收之后观察。

停止后应用几乎零分配 → Eden 装不满 → 不触发 Young GC → G1 不做 IHOP 检查 →
并发标记周期不启动 → 死掉的 humongous 对象（10MB byte[] 超过 region 一半大小，
直接分配在老年代）长期占着 O≈100%。实测：停止后观察 60 秒，
`YGC/CGC` 计数**全程冻结**、只有 E 缓慢爬升——没有任何 GC 发生。

此时一条命令立见分晓：

```bash
jcmd <pid> GC.run          # 显式触发
jcmd <pid> GC.heap_info    # used 244MB → 23MB, O 99.89% → 22%
```

**生产启示**：「删了缓存怎么内存没降」的工单，一半是等错了对象——
要么等 GC（低分配应用可能要等很久），要么主动 `jcmd GC.run` 验证；
另一半才是真泄漏（GC.run 后仍不降，回到 Step 3 的对照法）。
</details>

### 【根因】
static 集合当缓存只进不出（`HeapOomScenario.unboundedCache`）。

### 【修复对比】
```java
// ❌ 故障代码：无界缓存
private static final List<byte[]> CACHE = new ArrayList<>();
public void put(byte[] data) { CACHE.add(data); }

// ✅ 修复：有界 + 过期（三选一按场景）
private static final Map<String, byte[]> CACHE =
        Caffeine.newBuilder().maximumWeight(64L << 20)   // 上限 64MB
                .weigher((k, v) -> v.length)
                .expireAfterWrite(10, TimeUnit.MINUTES)  // 过期兜底
                .build();
// 大对象查询改分页/流式；批量导出走文件而非内存聚合
```

### 【预防】
- 缓存必须有界（Caffeine maximumSize/maximumWeight）+ 过期策略；
- 压测覆盖「数据量 10 倍增长」场景；OOM 前的堆基线上移告警（比 OOM 告警提前数天）。

### ⭐ Arthas 一键定位
```
dashboard                       # 堆/Metaspace 实时 + 线程 Top
heapdump --live /tmp/heap.hprof # 只dump存活对象, 拖进 MAT
vmtool --action getInstances --className java.util.ArrayList --limit 3   # 看大集合实例
```

## 场景 02 · Metaspace OOM：动态类/类加载器泄漏

**触发**：`POST /api/faults/oom-metaspace/trigger`（温和 2000 个加载器）
**crash 模式**：`?mode=crash` → 真 `OutOfMemoryError: Metaspace`

### 【模拟告警】
> 【P1告警】JVM 已加载类数 1 小时 8,412 → 41,308，Metaspace 61.9MB/64MB

### 【第0现场 · 可观测性视角】
- 指标：`jvm_classes_loaded` **单调上涨不回落**是最强信号（正常服务类数恒定）；
  Metaspace 使用率逼近 `-XX:MaxMetaspaceSize`。
- 日志：常见于 Groovy/表达式引擎/动态代理业务（规则引擎、报表模板）上线后。
- 链路无异常（类加载不直接影响 RT），靠指标告警发现。

### 【定位路线图】
```
jcmd GC.heap_info 看 Metaspace used 逼近 MaxMetaspaceSize → 确认类数上涨
(jcmd VM.metaspace / 控制台 loadedClassCount) → jcmd GC.class_histogram
看不到元数据(堆直方图无大头, 这是与堆OOM的分水岭) → 查代码: 谁在 defineClass
```

### 【分步排查】
**Step 1 · Metaspace 真实余量**：`jcmd <pid> GC.heap_info`
```
 Metaspace       used 46108K, committed 46912K, reserved 131072K
```
**used 逼近 -XX:MaxMetaspaceSize（本演练 65536K=64m）才是真危险**
（jstat 的 M 列为何也在 90%+？见顶部「阅读须知」①）。
趋势观察用 `jstat -gcmetacapacity <pid> 1000 5`（MC=committed 容量随泄漏增长）。
**Step 2**：`jcmd <pid> VM.metaspace | head`（看 Loaded classes 与 committed 细分）
**Step 3**：堆直方图 `jcmd <pid> GC.class_histogram | head -5` —— **没有异常大头**（区别于场景01），
但控制台 `/api/metrics` 的 loadedClassCount 持续上涨（实测从 9775 → 13277）。

### 【根因】
每个请求/任务 new 一个 ClassLoader 去 defineClass（动态代理、脚本编译），
加载器被持有 → 类永不卸载（类卸载条件：**类加载器本身可回收**）。

### 【修复对比】
```java
// ❌ 每次都 new 加载器编译脚本 → 类无限增长
Class<?> c = new GroovyClassLoader().parseClass(script);

// ✅ 缓存编译结果：脚本内容 hash → Class 复用；必须换加载器时先 close
private static final Map<String, Class<?>> COMPILED = new ConcurrentHashMap<>();
Class<?> c = COMPILED.computeIfAbsent(sha256(script), this::compileOnce);
```

### 【预防】
- MaxMetaspaceSize 显式设置（默认无上限，会吃光内存才倒下）；
- 监控 `loaded class count` 增速；动态类技术选型评审时问「类会不会被卸载」。

### ⭐ Arthas
```
dashboard            # Metaspace 使用实时可见
sc -d *MetaspaceMarker   # 查类详情; sm 看方法; jad 反编译确认动态生成的类
```

## 场景 03 · ThreadLocal 内存泄漏（隐性，无 OOM）

**触发**：`POST /api/faults/leak-threadlocal/trigger?rounds=4`（每轮 4 线程 × 10MB）

### 【模拟告警】
> 【P1告警】堆内存锯齿上移（Old 区 GC 后基线每 30min +18MB），无 OOM 但 Full GC
> 从 2 次/天 升至 9 次/小时，疑似内存泄漏

### 【第0现场 · 可观测性视角】
- 指标：堆基线**缓慢**上移（比场景 01 温和得多）+ FGC 频率趋势上涨；
- 链路/日志无异常 —— 这类泄漏靠「趋势告警」而非「故障告警」发现；
- 排查时机：低峰期，因为要主动触发 GC 做对照。

### 【定位路线图】
```
jstat 确认回收后不降 → jcmd GC.class_histogram 看 byte[] 大头 → jcmd GC.run 再看(仍不降!)
→ 泄漏但无业务引用 → 怀疑隐藏持有者: ThreadLocal/线程池 → dump 看引用链
(MAT: Thread.threadLocals → ThreadLocalMap.Entry[].value)
```

### 【分步排查】
**Step 1 · 强制 GC 后堆不降**：`jcmd <pid> GC.run && sleep 2 && jstat -gcutil <pid>`
<details><summary>为什么 GC 救不了</summary>

ThreadLocalMap 的 Entry.key 是**弱引用**（GC 会清掉 key），但 **value 是强引用**，
且 Entry 挂在**线程对象**上。线程池的线程常驻不死 → value 永远可达 → 泄漏。
只有线程死亡或同线程后续 set/remove 触发 stale entry 清理才会释放。
</details>

> 对照场景 01 的「GC 惰性」框：这里的 GC.run 是**诊断手段**（GC 后不降 = 泄漏证据）；
> 而场景 01 停止后不降是**回收未发生**（清了引用但没 GC 发生）。同一个命令两种用途。

**Step 2 · dump 找持有链**（crash 场景或手动 dump）：
MAT → `Path to GC Roots` → `Thread @ 0x... "tl-leak-pool" → threadLocals →
Entry[].value → byte[10485760]`。持有者是**线程**而非业务对象——这就是答案。

### 【根因】
线程池常驻线程上 `ThreadLocal.set(大对象)` 后不 `remove()`（`ThreadLocalLeakScenario`）。

### 【修复对比】
```java
// ❌ 任务结束不清
tl.set(new BigContext());
doBusiness();

// ✅ finally 必清（或 try-with-resources 的 ThreadLocal 模式）
try {
    tl.set(new BigContext());
    doBusiness();
} finally {
    tl.remove();   // 一行，但线上事故里它价值一辆车
}
```

### 【预防】
- 规范：ThreadLocal 与 finally/remove 成对出现（代码评审 checklist 项）；
- 大对象优先考虑方法参数传递而非 ThreadLocal；
- 线程池场景审计：入池任务用完的 ThreadLocal 是否清理。

### ⭐ Arthas
```
heapdump --live /tmp/h.hprof 后用 MAT 搜 ThreadLocalMap
vmtool --action getInstances --className java.lang.ThreadLocal --limit 10  # 看实例数
```

## 场景 04 · GC 风暴：内存不足伪装 CPU 高 ⭐误诊之王

**触发**：`POST /api/faults/gc-storm/trigger`（填 170MB 老年代 + 2 个分配风暴线程）

### 【模拟告警】
> 【P0告警】CPU 97%（阈值85%），但 QPS 无明显上涨；接口 RT 普涨、无单接口异常

### 【第0现场 · 可观测性视角】
- 指标：CPU 高 + **GC 耗时/频率同步飙升**（`jvm_gc_pause_seconds`）；
- 链路：RT 整体抖动但**无慢 Span**（耗在 GC 停顿，不在任何业务环节）；
- 「CPU 高 + 无慢Span + GC 告警」三件套出现 → 直接跳过业务代码排查。

### 【定位路线图】—— 场景 05 的镜像
```
top -Hp 找高CPU线程 → Thread.print 查无此 nid(!) → 线程名是 "GC Thread#N"/
"C2 CompilerThre" → 确认是 GC 线程在吃 CPU → jstat -gcutil 看 FGC 狂涨
→ 转入内存排查(场景01/03 的路线) 找出堆被谁占住
```

### 【分步排查】
**Step 1 · 找高 CPU 线程**
Linux: `top -Hp <pid>` 🍎 macOS: `jcmd <pid> Thread.print | sed -E 's/^"([^"]+)".*cpu=([0-9.]+)ms.*/\2 \1/' | sort -rn | head -5`
<details><summary>实测关键现象（Linux top 视角示意）</summary>

```
  PID  USER  %CPU  COMMAND           ← Linux: 高CPU线程名是 GC Thread#N
 8423  app  99.7  "GC Thread#5"      ← 不是你的业务线程!
 8424  app  98.2  "GC Thread#2"
 8425  app  96.8  "G1 Conc Refinement"
```
拿这些 ID 去 Thread.print 输出里 grep —— **查无此线程**：GC 线程是 JVM 内部线程，
不出现在 Java 线程 dump 的业务栈里。「找不到」本身就是最重要的线索。
</details>

**Step 2 · jstat 定罪**
`jstat -gcutil <pid> 1000 5`
<details><summary>实测输出（触发 6 秒后）</summary>

```
  S0    S1    E      O      M     CCS    YGC    YGCT    FGC    FGCT     GCT
  -    0.2   1.5   95.1   97.9  93.0   2600   1.747   1586   14.652   16.404
   ↑O=95%               ↑YGC=2600      ↑FGC=1586 次且 FGCT 持续累积
```
FGC 每 10 秒 +几十次、Old 恒定 95%+ = Full GC 空转（收不出空间，反复全收集）。
实测进程 CPU 391%（GC 线程并行工作）。
</details>

### 【根因】
长生命周期对象占满老年代（+ 分配风暴）→ G1 反复 Full GC → GC 线程吃满 CPU。
**CPU 是症状，内存才是病根。**

### 【修复】
- 应急：扩堆 `-Xmx` 可立刻缓解（有富余机器内存时）；
- 治本：按场景 01/03 路线找出老年代大头清理掉；
- 若是「堆确实太小」：重算容量（活跃数据 × 2~3 倍），并审视分配速率。

### 【预防】
- 告警把 CPU 与 GC 指标放同一块大盘（同屏可见防误诊）；
- 容量规划评审：堆 < 存活数据 × 2 是事故预备。
