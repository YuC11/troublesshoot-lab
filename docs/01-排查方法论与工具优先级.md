## 二、可观测性前置认知——真实生产的第一现场

> **原则：系统不接入、思维必须前置。** 生产环境几乎都有可观测系统（无论 SkyWalking
> 还是 OTel+Grafana）。登机器敲命令之前，第一现场永远是观测大盘。本演练场虽然
> 不部署观测组件，但每个场景手册的「第0现场」一节都带你走一遍观测视角。

### 2.1 信号四件套

| 信号 | 回答的问题 | 典型产品 |
|---|---|---|
| **Metrics 指标+告警** | 什么时间、哪个实例、什么指标异常、趋势如何 | Prometheus + Grafana、SkyWalking 指标 |
| **Tracing 链路** | 一次请求经过了谁、慢/错在哪个环节（Span） | SkyWalking、Jaeger/Tempo |
| **Logging 日志** | 具体错误的上下文、traceId 串联 | ELK、Loki |
| **拓扑/依赖图** | 故障在调用链的哪一跳、影响面多大 | SkyWalking 拓扑、服务网格图 |

### 2.2 两套主流方案能力对照

| 能力 | SkyWalking 全家桶 | OTel + Grafana LGTM |
|---|---|---|
| 接入方式 | `javaagent` 零代码侵入（国内最主流） | OTel SDK/agent，或 Spring 原生 Micrometer |
| 看链路 | 自带 UI：拓扑图 → Trace 瀑布图，鼠标点到底 | Tempo 存链路，Grafana Explore 看瀑布图 |
| 看指标 | OAP 聚合 JVM/服务指标，可推 Grafana | Prometheus 抓取，Grafana 大盘（业界最通用） |
| 日志关联 | agent 自动注入 traceId 到 logback pattern | OTel appender / Loki4j 推 Loki，traceId 可点击跳链路 |
| 告警 | OAP 告警规则 → 钉钉/企微/webhook | Prometheus Alertmanager / Grafana Alerts |
| 选型直觉 | 国内团队、要开箱即用的拓扑与追因 | 云原生标准、要厂商中立与可组合 |

### 2.3 边界：观测系统告诉你 WHERE，不告诉你 WHY

```
观测系统: 告警「troubleboot-lab 实例10.0.0.11 CPU 97%, /api/user/register P99 4s」
   ↓ 已缩小范围: 服务 → 实例 → 接口 → (链路瀑布图)嫌疑 Span
JVM 原生工具: top -Hp + jcmd Thread.print → 罪恶的那一行代码 / 直方图 → 罪恶的那个对象
   ↓ 给出根因
```

**衔接动作**：观测系统负责把「哪个服务/哪个接口」缩小到一个 IP；登机后第一件事
`./scripts/diagnose.sh` 留现场，然后按 §三 优先级下钻。

### 2.4 故障类别 × 可观测信号映射（看到什么 → 怀疑什么）

| 故障 | 指标/告警表现 | 链路/日志表现 |
|---|---|---|
| 堆 OOM | 堆使用率爬坡至 100%、进程重启告警、FGC 突增 | OOM 前接口批量超时，日志有 `OutOfMemoryError` |
| Metaspace | 已加载类数单调上涨、Metaspace 逼近上限 | 动态代理/脚本类业务日志 |
| 隐性泄漏 | FGC 频率周级趋势上涨、GC 后堆基线上移 | 无明显错误（这就是难点） |
| GC 风暴 | CPU 高**但**链路无慢 Span、QPS 无变化 | RT 整体抖动，无单接口异常 |
| 死循环 | 单实例 CPU 高、QPS 不变 | 特定接口 RT ∞；线程池逐步耗尽 |
| ReDoS | 仅个别含正则校验的接口超时 | 请求日志停在参数校验阶段 |
| 死锁 | 接口成功率跌、失败全是「等待响应超时」，无 5xx | 线程数不变但 worker 全挂起 |
| 线程池耗尽 | 仅走该池的接口 hang；其他接口正常 | 日志出现 `TaskRejectedException`（有界队列时） |
| 句柄泄漏 | 突发 `Too many open files`，DB/socket 全报错 | 连接类错误集中爆发 |
| 慢 SQL | 接口 P99 高 + DB 侧慢查询计数上涨 | 瀑布图 Span 停在 JDBC，DB 耗时占比高 |
| N+1 | 接口慢**但**慢查询日志干净（单条都快） | Span 总耗时高、SQL 条数多（需开 SQL 统计） |
| 慢外部依赖 | 下游服务 RT 先恶化，上游随后级联超时 | 瀑布图清晰看到时间耗在下游 Span |
| 锁竞争 | RT 随并发线性恶化 | 无外部依赖慢，纯自身排队 |
| 连接池耗尽 | DB 接口批量报「Connection is not available」 | 与慢 SQL 告警同期出现（因果） |

## 三、工具优先级总纲（P0 → P4，先无损后有损）

```
第0现场  观测大盘缩小范围（服务→接口→实例）          无需登机
P0 保命  摘流量 / diagnose.sh 留现场 / 重启恢复        分钟级
P1 快观测 top / jps / jstat -gcutil / actuator / 日志   10s级·无损
P2 定位层 top -Hp / jcmd Thread.print / lsof / ping     30s级·无损
P3 深入   jcmd GC.class_histogram / GC.run 对照 / EXPLAIN   分钟级·轻开销
P4 重操作 jcmd GC.heap_dump（STW 可能数十秒）/ JFR / MAT / Arthas attach    最后手段
```

### 3.1 分类工具矩阵（JDK 9+ 以 jcmd 为正统，JDK 8 对照见 3.2）

**内存类**（顺序即优先级，实测输出见 02 手册）：

1. `jcmd <pid> GC.heap_info` —— 一屏看清堆各区 + Metaspace 快照；
   看趋势用 `jstat -gcutil <pid> 1000`（jcmd 无流式采样，趋势观察 jstat 仍是正解——全文唯一解释处）
2. `jcmd <pid> GC.class_histogram | head -20` —— 活体对象直方图，找大头（byte[]? HashMap?）
3. `jcmd <pid> GC.run` 后重复 ①② —— 区分「缓存可回收」vs「真泄漏」
4. dump：OOM 自动落盘（`-XX:+HeapDumpOnOutOfMemoryError`），或手动 `jcmd <pid> GC.heap_dump <file>`；
   间歇性故障上 JFR 持续采集（`jcmd <pid> JFR.start settings=profile ...`）+ JMC 分析

**CPU 高**：

1. Linux: `top -Hp <pid>` 找最耗 CPU 线程 TID；🍎 macOS: 无线程级 top，用
   `jcmd <pid> Thread.print | grep 'cpu=' | sort` 按线程 CPU 时间排序（见 3.3）
2. Linux: `printf '%x\n' <TID>` 转 16 进制 → `jcmd <pid> Thread.print | grep -A 20 nid=0x<hex>`
   🍎 macOS: nid 为线程名后方括号十进制值，直接 `grep '\[<TID>\]'`
3. **栈里找不到该 nid → 高 CPU 的可能是 GC/编译器线程 → 回 jstat 验证**（场景04 核心）
4. 间隔 2~3s 连续 3 次 Thread.print，栈「钉」在同一处即坐实
5. Arthas `thread -n 3` 一条命令等价 1~2 步（生产最常用）

**线程/IO 类**：

1. `jcmd <pid> Thread.print` —— 死锁自动报告（`Found one Java-level deadlock`）、
   `grep -c 'BLOCKED' / 'WAITING'` 统计、看线程都在等什么
2. 线程总数 `jcmd <pid> Thread.print | grep -c '^"'`（对照监控趋势）
3. `lsof -p <pid> | wc -l` 句柄数 + `ulimit -n` 上限
4. 连接状态：Linux `ss -antp`（🍎 macOS `netstat -an`，见 3.3）

**接口慢**：

1. **分层第一锤**：`curl .../api/health/ping` —— ping 快 ⇒ 进程没死透/GC 没风暴，
   问题在特定链路；ping 也慢 ⇒ 进程级故障（GC/死锁/线程耗尽），回到 CPU/内存类方法
2. 接口计时/访问日志：确定慢在哪个接口、哪一段
3. `jcmd <pid> Thread.print` ×2~3：业务线程在等什么——
   `socketRead0` ⇒ 下游慢 ｜ `HikariPool.getConnection` ⇒ 连接池 ｜
   `waiting for monitor` ⇒ 锁 ｜ `executeQuery`/MySQL 栈 ⇒ SQL
4. SQL 则 `EXPLAIN` 看执行计划——判读三字段：`type`（`index` 全索引扫描与 `ALL`
   全表扫描同属扫描家族，都是坏信号）、`key`（是否命中预期索引）、`rows`
   （预估扫描行数；`possible_keys` 有名字而 `key=NULL` 即「有索引用不上」，见场景 12）

### 3.2 工具演进（JDK 8 → JDK 9+/21，本项目统一 jcmd 优先）

> JDK 9 起官方把 jcmd 作为诊断统一入口，一个 attach 覆盖线程/堆/GC/VM/JFR。
> jstack/jmap 是 JDK 8 时代的分立工具，新 JDK 上仍可用但属旧习惯；jhat 已随 JDK 9 移除。
> **教学话术**：不是「jstack 不能用」，而是「会 jcmd 的人在新机器上少背五个工具名」。

| 用途 | JDK 9+/21 正统（首选） | JDK 8 兼容（老服务器） |
|---|---|---|
| 线程栈+死锁 | `jcmd <pid> Thread.print`（输出与 jstack 同格式） | `jstack <pid>` |
| 堆对象直方图 | `jcmd <pid> GC.class_histogram` | `jmap -histo <pid>` |
| 堆分区信息 | `jcmd <pid> GC.heap_info` | `jmap -heap <pid>`（JDK9+ 已不可用） |
| 堆转储 | `jcmd <pid> GC.heap_dump <file>` | `jmap -dump:...` |
| 强制 GC | `jcmd <pid> GC.run` | `kill -37 <pid>`(Solaris)/可视化工具 |
| GC 趋势采样 | `jstat -gcutil <pid> 1000`（jcmd 无流式） | 同左 |
| dump 分析 | MAT / VisualVM / JFR+JMC | MAT（jhat 已移除） |
| 持续画像 | **JFR**: `jcmd <pid> JFR.start name=x settings=profile duration=120s filename=x.jfr` | 无（JFR 商用期外） |
| 命令自发现 | `jcmd <pid> help` —— 忘了子命令就 help | — |

### 3.3 🍎 macOS 与 Linux 命令差异对照

> 手册主线写 Linux 命令；本机（macOS）演练时差异如下，场景正文中逐处 🍎 标注。

| 用途 | Linux（生产标准） | 🍎 macOS（本机演练） |
|---|---|---|
| 线程级 CPU | `top -Hp <pid>` | 无线程级 top；用 `jcmd <pid> Thread.print \| sed -E 's/^"([^"]+)".*cpu=([0-9.]+)ms.*/\2 \1/' \| sort -rn \| head`；或 Arthas `thread -n 3` |
| nid 匹配 | 16 进制：`printf '%x' TID` 后 `grep nid=0x<hex>` | 10 进制：线程名后 `[TID]` 即 nid，直接 `grep '\[<TID>\]'` |

### 3.4 高频口径陷阱速记（场景正文只留指针，正主在此）

| 陷阱 | 正解 |
|---|---|
| **jstat M 列 ≈98 不是 Metaspace 要爆**：M = used/**committed**，JDK16+ 弹性元空间（JEP 387）让 committed 紧贴 used，常态 90%+——它不是 used/MaxMetaspaceSize | 真实余量看 `jcmd <pid> GC.heap_info` 的 **committed** 对比 `-XX:MaxMetaspaceSize`（本演练 96m）。场景 01 触发前后 M 都 98 正是此因；场景 02 才真正逼近上限 |
| 选项名是 `-gcmetacapacity` | **没有 `-gcmetaspace` 这个选项** |
| 海量小类加载器下 used ≪ committed（裸 JVM 实验：64m 墙下 10,765 个加载器时 used 仅 10.4MB、committed 恰 65,536KB 才 OOM） | **撞墙判定口径是 committed**，每加载器 committed ≈ 6KB ≈ 6.7× used(0.9KB)——详见场景 02 |
| GC 后堆没降 ≠ 没释放 | 见 §4.1 GC 惰性 |

## 四、跨场景通用机制（正主——场景正文只留「见 01 §四」指针）

### 4.1 GC 惰性：引用清空 ≠ 内存释放

内存释放要同时满足三个条件：① 对象不可达（`clear()` 只完成这一步）；
② **JVM 真的执行了一次覆盖老年代的回收**；③ 你在回收之后观察。

低分配应用停止写入后：Eden 装不满 → 不触发 Young GC → G1 不做 IHOP 检查 →
并发标记周期不启动——死掉的 humongous 对象（如 10MB byte[] 超过 region 一半，
直接分配老年代）可以长期占着 O≈100%（实测 60 秒 YGC/CGC 全程冻结）。
诊断特征：**YGC/CGC 计数冻结 + E 缓慢爬升 = 没有 GC 发生**；
一条命令立见分晓：`jcmd <pid> GC.run`（等价演练场 stop 内置的 System.gc()）。

**生产启示**：「删了缓存怎么内存没降」的工单，一半是等错了对象（等 GC 或主动 GC.run 验证），
另一半才是真泄漏（GC.run 后仍不降）。完整实测案例见场景 01 Step 5。

### 4.2 OOM 后的错误处理纪律：先救命动作，后记账

OOM catch 块里第一原则是**只做零分配的救命动作**（置标志/清引用/GC），全部成功后才能
拼字符串记账——字符串拼接的 invokedynamic 首次链接要在当前元空间/堆里定义新类，
资源打满时它自己就是二次 OOM 点（本演练台真实发生过：记账先行 → clear() 永远执行不到
→ 全部 HTTP 线程连环 OOM、停止接口不可达、SIGTERM 无法分发）。正反例代码见场景 02。

### 4.3 「停止即回落」契约

17 个场景的 stop 全部内置确定性恢复，**停止后无需等待 GC 或重启**：

| 类别 | stop 内置动作 | 仪表盘预期 |
|---|---|---|
| 内存类(01-04,17) | 清引用 + 显式 System.gc()（类卸载/Cleaner 同理），日志打印 before→after | 堆/Metaspace/类数/堆外水位立即回落 |
| CPU 类(05-07) | volatile 开关翻转 → worker 退出（07 额外 await 线程终结后再 GC） | CPU 秒级回落，堆不滞留 |
| 线程/IO(08-11) | 释放锁 / 重建线程池 / interrupt 全部泄漏线程 / 补 close 全部 fd | 锁·线程数·fd 立即回落 |
| 接口慢(12-16) | 停后台流量/占坑线程（16 在途查询最长 3s 收尾） | 接口耗时立即恢复 |

生产等价动作：修复代码 + 重启；演练场把它做成「一个 stop 可重复验证」。

## 五、演练与事故通用纪律

1. **一次只触发一个场景**——多故障叠加是定位的地狱模式。
2. **先留现场再动手**：`./scripts/diagnose.sh` 一键把线程 dump×2/直方图/堆信息/句柄
   固化到 `diagnostics/<时间戳>/`。瞬态故障不等慢条斯理的人。
3. **生产保命三步**（演练场用不上，但必须刻进肌肉记忆）：
   确认告警真实 → **摘流量**（下掉故障实例）→ 留现场后**重启恢复**，再事后分析。
   「先恢复再排查」与「保留现场慢慢查」的平衡：能摘流量就不急着重启。
4. **每个假设都要有证据支撑**：手册里所有命令输出字段就是证据链。

## 附录 · 本项目代码的设计模式（带新人读代码用）

| 模式 | 落点 | 为什么 |
|---|---|---|
| **Strategy 策略** | `core/FaultScenario` 接口 | 16 种故障各自独立成策略，新增场景零侵入 |
| **Template Method 模板方法** | `core/AbstractFaultScenario` | 触发/停止/状态登记的生命周期只写一遍，子类只管「怎么制造故障」 |
| **Registry 注册器** | `core/FaultScenarioRegistry` | Spring 注入自动收集全部策略，按 ID 路由 |
| **Builder 建造者** | `core/FaultStatus`（Lombok @Builder + @Value） | 不可变状态快照，并发安全直接序列化 |
| **Facade 门面** | `web/FaultController` | REST 层不认识具体故障，一套 API 治理全部场景 |
| **State 简化** | `core/FaultState` 枚举 | 用枚举+CAS 表达状态机，不为模式而造类层级 |
| Singleton / Factory | 交给 Spring IoC | 容器天然单例与工厂，不自造轮子 |
| 刻意不用 Observer | —— | 场景状态只有控制台一个消费方，事件总线是过度设计——**判断「不用什么」同样是工程能力** |

Lombok 使用规范：`@Slf4j` 日志、`@RequiredArgsConstructor` 构造注入、
`@Value/@Builder` 不可变 DTO。特别教学点：场景 11 的流泄漏代码**故意不用**
`@Cleanup`/try-with-resources——先见过事故，才懂规范为什么存在。
